# job-autopilot

Автоматический поиск вакансий и подача откликов. Один-два раза в день система сама
находит подходящие вакансии, отбирает их по CV, подаёт простые и присылает в Telegram
отчёт и вопросы по сложным.

Стек: Fastify 5, Prisma 7, SQLite, Vue 3 (Options API) и строгий TypeScript.
Каркас взят из jwx-framework, его демо-домены удалены.

**Состояние.** Работают вход, регистрация и сессии. Готова схема БД: `jobs`, `applications`,
`questions`, `answers`. Домен [`jobs`](docs/jobs.md) готов: HTTP API для своих вакансий и API
для этапов конвейера. Страница «Вакансии» пока пустая. Домен `searches` ([сборщик](docs/collector-plan.md)):
сохранённые поиски, их прогон `npm run collect` и история прогонов. Первый источник — LinkedIn
через залогиненный agent Chromium (брокер, только чтение). Отбора и подачи ещё нет.

Запуск, структура и проверки описаны в [docs/development.md](docs/development.md).

## Идея

```
systemd timer (1–2 раза в день, окно ~1 час)
   │
   ▼
1. Сбор        Playwright-скрипт: заданные поисковые URL (LinkedIn, Djinni, …)
               → карточки вакансий → текст описания. Без ИИ, дёшево и стабильно.
   │
   ▼
2. Отбор       локальная модель (Ollama, qwen3:4b):
               CV-summary + описание → {score, why, red_flags}
               score ≥ порога → в очередь на подачу. Дедуп по URL и компании.
   │
   ▼
3. Подача      по одной вакансии за раз:
               claude -p на DeepSeek (--settings) + Playwright MCP
               контекст: profile.md, answers.md (банк ответов), путь к CV, URL
               DeepSeek сам классифицирует вакансию:
                 • простая (все поля известны) → заполняет → submit → скриншот
                 • сложная (неизвестные поля, тестовое, эссе) → НЕ подаёт,
                   возвращает список вопросов
               Выход: строгий JSON {status, questions[], screenshot, session_id}
   │
   ▼
4. Telegram    • отчёт: «подал в X, Y; пропустил Z (почему)»
               • вопросы по вакансии, ответ пишешь прямо в чат
               → ответ сохраняется в банк ответов (в следующий раз вопроса не будет)
               → подача продолжается: claude --resume <session_id>
```

### Почему поиск не делает локальная модель

Железо: GTX 1060 6GB и 16GB RAM, то есть реально модели на 3–4B. Снимок одной страницы
LinkedIn весит 10–50k токенов, и на таком железе модель обрабатывает его минуты. Модели
на 4B в многошаговой работе с браузером теряют цель и зацикливаются. Поэтому вакансии
собирает детерминированный скрипт, а локальная модель решает узкую задачу: оценить
текст вакансии против CV. С этим она справляется.

Если позже появится GPU мощнее, этап «Сбор» можно отдать агенту, интерфейс между
этапами от этого не меняется.

## Пользователи и данные

Система рассчитана на нескольких пользователей. Каждый регистрируется сам, и всё, что
относится к поиску работы, принадлежит ему:

- `jobs.userId` — у каждого своя выдача. Дедупликация идёт по `(userId, url)` и
  `(userId, source, externalId)`, поэтому одну и ту же вакансию два пользователя видят независимо.
- `answers.userId` — свой банк ответов. Ключ вопроса уникален в пределах пользователя.
- `applications` и `questions` принадлежат пользователю через свою вакансию.

Сервисы всегда получают пользователя явно и фильтруют по нему. Сгенерированный CRUD
этого не умеет, поэтому домены вакансий пишутся вручную.

## Компоненты

| Компонент | Где | Что делает | Состояние |
|---|---|---|---|
| Домен `users` | `server/src/users` | регистрация, вход, сессии в HttpOnly cookie | готов |
| Схема БД | `server/prisma/schema.prisma` | `jobs`, `applications`, `questions`, `answers` | готова |
| Домен `jobs` | `server/src/jobs` | вакансии пользователя: выдача, ручное добавление, статусы, API для сборщика и scorer — [docs/jobs.md](docs/jobs.md) | готов |
| Домен `searches` | `server/src/searches` | сохранённые поиски, прогон сборщика, история прогонов, модули источников (remote-доски, LinkedIn, …) | ядро и LinkedIn готовы — [план](docs/collector-plan.md) |
| Домены `applications`, `questions`, `answers` | `server/src/…` | попытки подачи, вопросы агента, банк ответов | план |
| `scorer` | плагин Ollama | JSON-оценка вакансии против CV | план |
| `applier` | обёртка над `claude -p` | запуск DeepSeek с MCP, разбор JSON-результата, таймауты | план |
| `telegram` | плагин Bot API | отчёты, вопросы, приём ответов, кнопки ✅/❌ | план |
| `run` | CLI + systemd timer | один цикл: сбор → отбор → подача → отчёт, в пределах окна | план |
| Клиент | `client/` | вход, регистрация, профиль; дальше вакансии, вопросы, подачи | частично |

Профиль кандидата (CV, `profile.md`, поисковые запросы, порог score) тоже принадлежит
пользователю. Пока это не хранится нигде. Где его держать (таблицы или файлы вне Git),
решим на этапе сборщика.

### Статусы

- **Вакансия:** `found → scored → rejected | queued → applying → applied | needs_input | failed | skipped`
- **Вопрос:** `open → answered → used`

## Защиты (с первого дня)

- **Режим «стоп перед Submit»** первые 1–2 недели: DeepSeek заполняет форму и присылает
  скриншот в Telegram, решение принимаешь ты (✅/❌). Автоподачу простых вакансий включаем,
  когда появится доверие.
- Лимиты: не больше N подач за запуск, не больше $X на DeepSeek в день, тайм-аут на одну
  вакансию, весь запуск укладывается в окно (~1 час).
- Агенту запрещено создавать аккаунты, платить, вводить пароли и проходить капчу. Такие
  вакансии становятся «сложными» и уходят тебе в виде вопроса.
- Браузер с постоянным профилем, в котором ты уже залогинен. Пароли агенту не передаются.
- Playwright MCP (`:8931`) — один общий браузер, поэтому подачи идут строго по одной.
- Каждая подача логируется: скриншот до и после, итоговый JSON, токены и стоимость.

## Порядок сборки

Сначала результат, потом инфраструктура. Следующий этап начинается только после того,
как предыдущий реально работает.

1. **Сбор.** Модульный collector, вакансии пользователя в `jobs`, дедупликация, страница
   «Вакансии». Критерий: ежедневный прогон по 2–3 сайтам без дублей. План —
   [docs/collector-plan.md](docs/collector-plan.md).
2. **Подача по URL.** `apply <url>` → DeepSeek + MCP → JSON-отчёт в консоль, режим
   «стоп перед Submit». Критерий: 5 реальных вакансий заполнены корректно.
3. **Telegram и банк ответов.** Отчёты, вопросы, приём ответов, `--resume`, кнопки ✅/❌.
4. **Отбор.** Scorer на Ollama: `found → scored → queued | rejected`.
5. **Расписание и автоподача.** systemd timer, лимиты и окно, автоподача простых вакансий.
