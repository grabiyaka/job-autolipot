# Архитектура

Документ описывает соглашения сервера на Fastify, Prisma 7 и TypeScript.
Клиент описан в [frontend.md](frontend.md): компоненты, состояние, API и SCSS.
Каркас задаёт структуру, способ передачи зависимостей и границы ответственности.
Состав доменов, модель данных и бизнес-правила определяет приложение job-autopilot.

Зависимости объявляются явно: автокомплит, переход к определению и безопасное переименование
работают средствами обычного TypeScript.

Сейчас в коде два домена: `users` (регистрация, вход, сессии) и [`jobs`](jobs.md)
(вакансии пользователя). Примеры ниже используют `jobs`; часть имён в них условная,
настоящий состав файлов домена описан в [jobs.md](jobs.md).

## Структура проекта

```text
client/
  src/
    components/                страницы по сущностям и общие UI-компоненты
    store/                     Pinia stores
    router/                    маршруты клиента
    assets/css/                общие стили, переменные и responsive-миксины
    App.vue
    main.ts
  package.json                 зависимости и проверки клиента
server/
  app.ts                       сборка HTTP-приложения
  server.ts                    запуск сервера
  framework/
    core/                      общие типы без инфраструктурных зависимостей
    composition/               связывание реализаций и подключение доменов
    http/                      общие технические HTTP-схемы
    generator/                 инструменты генерации, не runtime приложения
  plugins/                     недоменные технические возможности
  middlewares/                 идентификация и уровни HTTP-доступа
  generated/prisma/            сгенерированный Prisma Client, вне Git
  prisma/
    schema.prisma              модель данных приложения
    domains.json               поля и операции генерируемых доменов
    migrations/                версионируемые миграции
  src/                         домены непосредственно в корне
    users/                     регистрация, вход, сессии
    jobs/                      вакансии пользователя
  data/                        файл SQLite, вне Git
  tests/
  scripts/
  package.json                 зависимости и проверки сервера
docs/                          общая документация
scripts/                       запуск и настройка всего проекта
Dockerfile                     сборка клиента и сервера
compose.yaml                   приложение и том с файлом БД
AGENTS.md                      общие правила и ссылки на документацию
package.json                   команды из корня для обеих частей
```

Если ниже путь указан без `client/` или `server/`, он относится к корню `server`.
Команды `npm run …` в документации запускаются из корня репозитория, если не указано другое.
У клиента и сервера отдельные `package.json` и lock-файлы. Общий root-пакет предоставляет
команды запуска, генерации и проверок; runtime-зависимости ему не принадлежат.


В `src` лежат непосредственно домены. Домен объединяет данные и сценарии одной предметной
области. Обёртка `src/domains` и технические папки внутри `src` не нужны.

Внутри домена используем плоскую структуру. Роли разделены файлами, без обязательных подпапок
`application`, `business`, `http`, `infrastructure` или `ports`.
Создаём только необходимые файлы: домен не обязан иметь репозиторий, HTTP-вход,
отдельный расчёт или историю, если они ему не нужны.

`framework` содержит общую основу и место сборки приложения. Размещение
`framework/composition` не делает конкретную сборку универсальной: этот код знает домены
и инфраструктуру своего приложения. Из него передаются реализации общих и доменных интерфейсов.

В общую основу можно добавлять технические механизмы конфигурации, обработки ошибок,
жизненного цикла или наблюдаемости по мере необходимости.
Предметные понятия и правила принадлежат приложению; перенос в `core` не должен служить
способом обойти границы доменов. `core` не зависит от Fastify, Prisma и инфраструктурных библиотек.

`plugins` и `middlewares` остаются отдельными папками в корне `server`.
`generated` также находится в `server`, отдельно от `framework` и `src`: это воспроизводимый
результат генерации, исключённый из Git. Его не редактируем вручную.
После изменения схемы используем `npm run db:generate`.
Сама схема и миграции находятся в `prisma` и хранятся в репозитории приложения.

`db:generate` также обновляет CRUD-домены из `prisma/domains.json`.
В отличие от Prisma Client, эти файлы находятся в `src` и хранятся в Git:
сгенерированные блоки соседствуют с сохраняемыми ручными расширениями.
Типы полей получаются из одной Prisma-модели; конфигурация выбирает публичные поля и операции.
Определения DTO физически остаются в `*Types.ts`, схемы — в `*Routes.ts`,
без реэкспорта Prisma-типов. Подробности — в [руководстве генератора](generator.md).

## Нейминг и роли файлов

Папки доменов называем по-английски, во множественном числе и нижнем регистре: `jobs`.
Доменные файлы — PascalCase, сущность в единственном числе и роль: `JobService.ts`.
Если файл содержит основной класс, имя класса совпадает с именем файла.
Функции и методы — lowerCamelCase с названием предметного действия:
`recordFound`, `requireOwnedBy`, `sortedByScore`.
Соглашение PascalCase относится к доменным файлам; технические файлы вроде
`create-application.ts` сохраняют свой стиль.

Домен по умолчанию состоит из четырёх файлов (так устроен `jobs`):

| Файл | Ответственность |
| --- | --- |
| `JobRoutes.ts` | Маршруты домена, JSON-схемы запросов и ответов, подключение middleware. |
| `JobController.ts` | Получить HTTP-ввод и актора, вызвать сервис, сформировать HTTP-ответ. |
| `JobService.ts` | Типы и статусы домена, проверки и сценарии: доступ, переходы, вызовы репозитория. |
| `JobRepository.ts` | Хранение через Prisma и преобразование записей БД в типы домена. |

Зависимости идут цепочкой: Routes → Controller → Service → Repository. Routes ещё может брать
у сервиса константы для схем (например, список статусов). Пропускать слой нельзя:
Routes и Controller не импортируют Repository.

Дополнительные файлы заводятся по необходимости, а не по шаблону:

| Файл | Когда нужен |
| --- | --- |
| `*Types.ts` с интерфейсом `*Api` | Домен понадобился другому домену: между доменами импортируются только `*Types.ts`. |
| `*Contracts.ts` | Нужна подмена репозитория или атомарный сценарий с Unit of Work. |
| `*Rules.ts` и предметные помощники | Логика сервиса разрослась настолько, что её трудно читать. |
| `*Mapper.ts` | Преобразование данных хранения стоит отделить от репозитория. |

Домен `users` устроен по полной схеме (`UserTypes`, `UserContracts`, `UserRules`), потому что
его API нужен middleware аутентификации. Имя помощника должно объяснять данные или действие;
универсальные `helpers.ts` и `utils.ts` для несвязанных задач не нужны.

`*Types.ts` — принятое имя публичной границы вместо `public.ts`.
Интерфейс внутри называется `UserApi` и т. п.
В файл входят необходимые потребителям контракты; внутренние типы не собираем туда
ради удобства импортов. Конкретные сервисы, репозитории и Prisma-типы через него не экспортируем.
`*Contracts.ts` содержит внутренние порты, например `UserRepositoryContract`,
а при необходимости атомарного сценария — Unit of Work.

Суффикс `*Mapper.ts` сейчас обозначает инфраструктурную роль в проверке архитектуры.
Чистые помощники подготовки данных называем по их предметному назначению;
`*CalculationData.ts` подходит для расчётов, но не является обязательным именем для любого сценария.
При росте правила можно разделить на несколько предметных сценариев; обязательного
переименования всех `*Rules.ts` или создания дополнительных папок нет.

## DI и границы доменов

Контроллер или сервис может обращаться к публичному API любого нужного домена.
Для этого он явно объявляет зависимость от соответствующего интерфейса.
Зависимость передаётся через конструктор и видна в типах.

Пример конструктора сервиса вакансий:

```ts
constructor(
  private readonly jobs: JobRepository,
  private readonly users: UserApi,
) {}
```

`JobRepository` импортируется как тип из собственного `JobRepository.js`,
а `UserApi` — из `../users/UserTypes.js`. Конкретные реализации передаёт composition root.
Сервис не создаёт репозитории и чужие сервисы самостоятельно.
Каждый потребитель получает необходимые ему зависимости; весь реестр сервисов не передаётся.

| Потребитель | Что ему доступно |
| --- | --- |
| Routes | Свой контроллер, константы своего сервиса, публичные типы, middleware и HTTP-механизмы. |
| Controller | Свой сервис, публичные API нужных доменов, HTTP-запрос и общие типы. Репозитории недоступны. |
| Service | Свой репозиторий (напрямую или через контракт), свои правила, публичные API других доменов, необходимые общие порты. |
| Rules и чистые предметные помощники | Данные, публичные типы, свои чистые помощники и `core`; без вызовов инфраструктуры и сервисов. |
| Repository и Mapper | Своя инфраструктура хранения и доменные контракты. Чужие внутренние модули недоступны. |
| Composition | Конкретные реализации для создания и связывания приложения. |

Любой импорт из другого домена проходит через его `*Types.ts`.
Сервис не импортирует чужой `Repository`, `Contracts`, `Rules` или конкретный `Service`.
Контроллер не получает даже свой репозиторий и не импортирует его контракт.
Сервис не импортирует Prisma: работа с БД остаётся в репозитории.
Публичный API описывает действия домена, а не открывает наружу Prisma или универсальный CRUD-репозиторий.

Не используем строковый `container.get('service')`, динамическое добавление зависимостей через
`Object.assign`, глобальный локатор сервисов или передачу полного Fastify в сервис.
Для DI не требуются декораторы, reflection или расширение редактора.
`any` и утверждения типов не должны скрывать необъявленные зависимости.

Граф зависимостей экземпляров сервисов поддерживаем без циклов. Связи только между типами
сами по себе не создают такой цикл. Если два сервиса требуют друг друга, пересматриваем
владельца сценария: общую последовательность может выполнять отдельный осмысленный сервис,
зависящий от обоих публичных API. Ленивый поиск в контейнере скрывает эту проблему.

Сервисы могут жить всё время работы приложения, если не хранят состояние текущего запроса.
Актор, входные данные и транзакционный контекст передаются на вызов; поля `currentUser`
или `currentRequest` в общем экземпляре недопустимы.

## Читаемый бизнес-слой

Бизнес-слой — логическое разделение плоских файлов домена.
`*Rules.ts` позволяет прочитать сценарий как последовательность предметных действий.
Смысл правил должен быть понятен человеку, который знает предметную область,
даже если он не знаком с Fastify, Prisma или устройством TypeScript.

Условный пример постановки вакансии в очередь на подачу:

```ts
job.requireOwnedBy(actor);
job.requireStatus('scored');

return job.score >= threshold ? job.queued() : job.rejected(reasons);
```

Имена показывают проверки и результат действия. Подробности, например допустимые переходы
статусов, реализуют чистые предметные методы. Здесь `queued` и `rejected` возвращают новое
значение, а запись в БД выполняет сервис через репозиторий.

Для подготовки списка вместо технического `jobs.sort((a, b) => ...)` в сценарии уместно
`jobs.sortedByScore()`, если это выражает понятие предметной области.
Это принцип нейминга, а не требование оборачивать каждую коллекцию в класс.

| Что мешает чтению сценария | Где находятся подробности |
| --- | --- |
| Разбор строк, нормализация и преобразование единиц | Именованный чистый помощник или предметный объект. |
| Подготовка нескольких значений и большой объект результата | Предметный помощник с методом вроде `assignmentResult`; для расчётов возможен `*CalculationData.ts`. |
| Сортировка, фильтрация, построение представления | Чистый предметный метод с понятным названием. |
| Преобразование строк БД или сохранённого JSON | Repository или `*Mapper.ts`. |
| HTTP-заголовки, статус ответа, транспортная сериализация | Routes / Controller и общая HTTP-инфраструктура. |
| Загрузка и запись данных, время или ID | Service через явно переданные зависимости. |

Небольшой объект с именованными значениями допустим.
Длинное перечисление полей с преобразованиями прячем за понятным методом сборки результата.
Значимые решения и порядок действий остаются видимыми; весь сценарий не должен исчезать
за безымянным `process()` или цепочкой со скрытым изменением состояния.

`CalculationData` и другие помощники могут реализовывать отдельные проверки и вычисления;
они не обязаны быть только DTO-мапперами. Разделение проходит между читаемым сценарием
и деталями его исполнения. В сервисе остаются проверки, требующие I/O или согласованного
состояния хранения. Требования «все условия находятся только в Rules» нет.

Чистые правила и их помощники не обращаются к БД, сети, файловой системе, переменным окружения,
текущему времени или генератору ID. Одинаковые входные данные дают одинаковый результат.
Под красивым именем метода нельзя скрывать вызов сервиса или другую внешнюю операцию.
Нужные время, настройки и данные сервис получает явно и передаёт в расчёт.

## HTTP, плагины и доступ

HTTP-маршруты принадлежат доменам и находятся в `*Routes.ts` вместе с JSON-схемами запросов
и ответов. Отдельный `*Schemas.ts` для них не заводим.
Composition подключает маршруты к приложению. Общие технические схемы, например схема ошибки,
находятся в `framework/http`; недоменные технические маршруты могут подключаться плагинами.

Плагины содержат недоменные возможности: подключение и закрытие БД, интеграцию логирования,
внешних клиентов и других технических средств с Fastify. Конкретный набор выбирает приложение.
Бизнес-правила в плагинах не размещаем. Сервис получает узкий интерфейс нужной зависимости,
а composition связывает его с реализацией.

Middleware отвечает за идентификацию и начальные уровни HTTP-доступа.
Роли, разрешения и правила владения данными определяются приложением.
Фреймворк не должен закреплять конкретные названия ролей или идентификатор одной сущности
в качестве универсальной модели доступа.

Идентификация JWT и проверка сохранённой сессии находятся в `middlewares/authentication.ts`.
Уровни доступа подключаются отдельными явными импортами в доменных маршрутах:
`publicAccess`, `authenticatedAccess`, `adminAccess` и `rolesAccess(...roles)`.
Они передаются Fastify через `preHandler`; динамического поиска middleware или прикрепления
методов доступа к серверу нет. Роли приложения — `admin` и `user`: `authenticatedAccess`
допускает любого вошедшего, `adminAccess` — только admin, у `rolesAccess` точный
типизированный список без наследования прав.
Полная матрица и примеры находятся в [руководстве авторизации](authentication.md#роли-и-middleware-в-маршрутах).

Сервис и правила проверяют допустимость операции и доступ к конкретным данным,
когда этого требует сценарий. Проверки сохраняются при вызове из другого домена,
фоновой задачи или теста, минуя HTTP.
Контекст актора передаётся обычными типизированными данными, без Fastify Request.
Middleware и плагины также не импортируют внутренние модули доменов.
Чистый `requireRole` из `core/roles.ts` позволяет использовать одинаковые определения
ролей в HTTP и сервисах. Проверка роли не заменяет проверку владельца: вакансии, подачи,
вопросы и ответы принадлежат пользователю, и сервис фильтрует их по `actor.id`.

Схемы описывают свои контракты: вход проверяет новый HTTP-запрос, ответ — возвращаемые данные.
Если приложение хранит исходные запросы или историю, их формат не обязан совпадать
с текущими ограничениями нового ввода. Для такого сценария нужны самостоятельные схемы ответа.

## Клиент и аутентификация

Vue-клиент обращается к HTTP API. Он не импортирует серверные репозитории, сервисы или Prisma Client.
Публичные транспортные типы домена допускается импортировать через `import type`, если они не зависят
от Node.js, Fastify или Prisma. Это сохраняет один источник DTO и удаляется из клиентской сборки.
Наличие TypeScript-типа не заменяет серверную проверку HTTP-ввода.

Компоненты используют Options API. HTTP-транспорт, состояние входа, маршрутизация и общие стили
имеют отдельные именованные модули; детали описаны в [руководстве клиента](frontend.md).
В Docker Fastify отдаёт готовую клиентскую сборку и API с одного origin.
В разработке Vite проксирует API на Fastify.

JWT передаётся браузеру в HttpOnly cookie. Установку, проверку и удаление cookie выполняет
HTTP-слой; сервисы получают типизированный Actor. Сам токен не является единственным источником
состояния доступа: сохранённая сессия позволяет отозвать вход при logout, а текущая запись
пользователя определяет действующие права. Защита запросов cookie и конфигурация описаны в
[руководстве авторизации](authentication.md).

Названия ролей и связь пользователя с предметной сущностью остаются настройками приложения.
Добавление входа не отменяет проверки доступа в сервисах и не делает роли текущего примера
универсальной моделью для каждого будущего проекта.

## Хранение и дополнительные механизмы

Приложение выбирает модель хранения и требования к согласованности по своим сценариям.
Универсальность не означает, что каждому домену нужны версии, ключ идемпотентности,
неизменяемый журнал, события, снимки или операция отмены.

| Требование сценария | Подходящий механизм |
| --- | --- |
| Несколько изменений должны сохраниться вместе | Транзакция БД; при участии нескольких доменов — Unit of Work и их публичные контракты. |
| Нужно обнаружить параллельное изменение | Проверка версии или другая подходящая стратегия конкурентного доступа. |
| Повтор внешней команды не должен повторять эффект | Идемпотентность с определёнными правилами сравнения запросов. |
| Нужно объяснить прошлые действия | Аудит, история изменений или журнал событий с требованиями этого приложения. |
| Бизнес-решение зависит от времени или случайного ID | Явная зависимость, например `Clock` или `Identifiers`. |

Для атомарного изменения нескольких доменов интерфейс UoW принадлежит сценарию,
а инфраструктурная реализация находится в composition. Она создаёт зависимости
на одной транзакции БД и передаёт сервису ограниченные публичные возможности участников.
Сервис не импортирует чужой репозиторий ради общей транзакции и не получает Prisma transaction.

Состав публичного API определяется задачей. Он может содержать чтение и запись;
разделять их на отдельные интерфейсы стоит, когда это делает права и зависимости понятнее.
Универсального требования делать основной `*Api` доступным только для чтения нет.

Внешние вызовы не становятся атомарными от оборачивания кода в транзакцию БД.
Способ согласования с внешними системами определяется конкретным сценарием;
готовая универсальная распределённая транзакция здесь не заявляется.

Форматы данных, единицы измерения, точность и округление принадлежат предметной области.
Публичные DTO не содержат Prisma-типы; инфраструктура переводит данные в контракты домена.
Обычный CRUD, аудит изменений и хранение событий допустимы там, где они соответствуют
требованиям приложения. Сам фреймворк не предписывает запрет обновления или удаления всех записей.

## Проверки и добавление доменов

При добавлении домена:

1. Определить владельца данных, сценарии и нужные публичные входы/результаты в `*Types.ts`.
2. Описать правила понятными предметными действиями; выделить помощники там, где они упрощают чтение.
3. Объявить необходимые зависимости сервиса, внутренние порты разместить в `*Contracts.ts`.
4. Реализовать хранение и дополнительные механизмы только под требования сценария.
5. Если нужен HTTP, добавить Controller и Routes со схемами; связать реализации в composition.
6. Проверить правила, доступ, границы импортов и поведение затронутой инфраструктуры.

Для обычного CRUD эти файлы может подготовить генератор. Его шесть файлов — выбранный
шаблон CRUD, а не обязательный набор для каждого ручного домена. Бизнес-сценарии, политика
доступа и подключение остаются явными. Сгенерированная policy проверяет операцию в целом;
владение записью и фильтрация по организации требуют собственного сервиса/репозитория.
Для HTTP-проверок `register*CrudRoutes` принимает необязательный четвёртый аргумент
`*RouteAccess`: middleware по операциям list/get/create/update/delete. Его передаёт
ручная обёртка `register*Routes` вне защищённого блока. Шаблон не знает названий ролей,
а обязательная policy сервиса продолжает работать при прямых вызовах без HTTP.

[Проверка архитектуры](../server/scripts/check-architecture.ts) запускается командой
`npm --prefix server run architecture`,
входит в `npm run check` и в сборку Docker. Она анализирует импорты через AST TypeScript,
включая алиасы, реэкспорты и динамические импорты.

Роль доменного файла определяется суффиксами `Routes`, `Controller`, `Service`, `Repository`,
`Contracts`, `Mapper`; файлы `*Types.ts` непосредственно в папке домена служат публичной границей.
Остальные файлы по умолчанию считаются чистыми бизнес-модулями.
Prisma и generated доступны Repository/Mapper, plugins и composition.
Контракты не должны протаскивать наружу реализации.

Отдельное исключение для инструментов — `framework/generator`: они читают метаданные Prisma
при разработке. Проверка запрещает runtime-модулям импортировать генератор и запрещает
самому генератору зависеть от конкретных доменов и сборки приложения.
Сгенерированный домен подчиняется обычным правилам импортов.

Это статическая проверка импортов. Она не доказывает отсутствие циклов DI, отсутствие I/O
через глобальные функции, читаемость правил, правильность имён или плоскую структуру.
Имя `*Types.ts` само по себе не гарантирует хороший публичный контракт.
Эти свойства проверяем при разработке и ревью.
TypeScript-интерфейсы и DI не изолируют недоверенный код во время исполнения.

`npm run domain:check` проверяет актуальность защищённых блоков без записи и входит в `npm run check`.
Для изменений поведения используем `npm run check` и необходимые интеграционные проверки.
Они создают временную SQLite-БД через `createTestDatabase()` из `server/tests/auth-fixture.ts`.
Тесты не должны сбрасывать данные работающего приложения.
Для правок только документации достаточно сверить текст с кодом и проверить ссылки.

## Принципы и текущее состояние

Потребность одного домена не становится обязательной возможностью каждого нового домена.
Версии, аудит, события и Unit of Work выбираются под задачу.

Общая ошибка `ApplicationError` содержит `statusCode`. Бизнес-модули не импортируют Fastify,
но связь с соглашениями HTTP пока остаётся.
