# Вход по JWT

Клиент входит по email и паролю. Сервер создаёт сессию в PostgreSQL и выдаёт JWT
в cookie `framework_session`. Сам JWT не возвращается в JSON и не хранится в localStorage.

Cookie имеет `HttpOnly`, `SameSite=Lax`, `Path=/api`; `Secure` включается для HTTPS.
По умолчанию вход действует один час. Refresh-токена и автоматического продления нет:
после истечения срока пользователь входит снова.

## Создать пользователя

В Docker после запуска и применения миграций:

```bash
docker compose exec api npm run user:create -- --email admin@example.com --name Admin --role admin
```

Для локального backend из корня репозитория (после установки зависимостей, генерации и миграций):

```bash
npm --prefix server run build
npm run user:create -- --email admin@example.com --name Admin --role admin
```

CLI запускает скомпилированный `server/dist/scripts/create-user.js`; в Docker он уже собран.
Команда запрашивает пароль без отображения в терминале; длина — 12–128 символов.
Пароль не принимается как CLI-аргумент или переменная окружения.
Для автоматизации поддержан ввод одной строки через stdin из выбранного секретного хранилища.
Не сохраняй исходный пароль в репозитории, истории команд или логах CI.

CLI без `--role` создаёт `manager`. Для администратора укажи `--role admin` явно,
как в командах выше. Значение Prisma по умолчанию — `foreign`: создание записи без
явной роли не выдаёт права сотрудника. Публичной регистрации и встроенного администратора
с общим паролем нет. Команда принимает `admin`, `manager`, `guest`, `foreign`.

Для предметного примера можно связать гостя с абонентом:

```bash
npm run user:create -- --email subscriber@example.com --name Subscriber \
  --role guest --subscriber-id demo-subscriber-1
```

Связанный абонент должен существовать. У `guest` связь необязательна; другие роли
не могут иметь `subscriberId`. Гость без связи остаётся обычным пользователем приложения,
но не получает доступ к чужим лицевым счетам.

## Роли и middleware в маршрутах

Текущий набор ролей повторяет `zijn-crm`: `admin`, `manager`, `guest`, `foreign`.
`foreign` — авторизованный пользователь без доступа к рабочим разделам;
отсутствие входа представлено отсутствием актора, а не этой ролью.
Названия ролей и их возможности принадлежат приложению: новый проект может определить
другую модель прав. Активные роли объявлены в [core/roles.ts](../server/framework/core/roles.ts).

Каждый уровень доступа экспортируется из отдельного файла:

| Middleware | Кто допускается |
| --- | --- |
| [publicAccess](../server/middlewares/publicAccess.ts) | Любой посетитель, включая пользователя без входа. |
| [authenticatedAccess](../server/middlewares/authenticatedAccess.ts) | Любая действующая сессия, включая `foreign`. |
| [guestAccess](../server/middlewares/guestAccess.ts) | `admin`, `manager`, `guest`. |
| [generalAccess](../server/middlewares/generalAccess.ts) | `admin`, `manager`. |
| [adminAccess](../server/middlewares/adminAccess.ts) | Только `admin`. |
| [rolesAccess(...roles)](../server/middlewares/rolesAccess.ts) | Только явно перечисленные роли. |

Middleware подключается обычным импортом в доменный `*Routes.ts` через `preHandler`.
Например, внутри регистрации маршрутов с уже созданным контроллером:

```ts
import { generalAccess } from '../../middlewares/generalAccess.js';
import { rolesAccess } from '../../middlewares/rolesAccess.js';

server.post('/api/projects', {
  preHandler: generalAccess,
  // schema: схемы запроса и ответа этого домена
}, controller.create);

server.get('/api/projects/special-view', {
  preHandler: rolesAccess('admin', 'guest'),
}, controller.specialView);
```

`rolesAccess('admin', 'guest')` не допускает `manager`: список точный, автоматического
наследования прав нет. Имена ролей типизированы и доступны в автокомплите; пустой список
или неизвестная роль отклоняются. При необходимости Fastify принимает массив middleware
в `preHandler`. Динамического `server.access` или регистрации middleware по строковым именам нет.

Без действующей сессии защищённый маршрут отвечает `401`; с подходящей сессией,
но запрещённой ролью — `403`. `publicAccess` явно обозначает публичность маршрута,
но не отключает общие проверки Origin, CSRF и ограничения частоты запросов.
Login и logout публичны; `/api/auth/me` использует `authenticatedAccess`.

В примере задач список и карточка доступны `admin/manager/guest`, создание и изменение —
`admin/manager`, удаление — только `admin`. `foreign` может войти, посмотреть свой профиль
и выйти, но не работать с задачами. Клиент скрывает недоступные действия;
HTTP-маршруты и сервис проверяют те же ограничения независимо от интерфейса.
Подключение уровней к сгенерированному CRUD описано в [руководстве генератора](generator.md#подключение-и-доступ).

HTTP-проверка не заменяет авторизацию сценария. В сервисе используй обычный Actor
и чистые `requireRole` / `hasGeneralAccess` из `core/roles.ts`; привязку к конкретной записи
или организации проверяй отдельно. Так прямой вызов сервиса из другого домена
не обходит правила доступа.

## Обновление ранее созданных пользователей

Миграция `20261008040000_application_roles` переименовывает `operator` в `manager`,
`subscriber` в `guest` и добавляет `admin` и `foreign`. Пользователи, пароли, связи с абонентами
и сессии сохраняются; автоматического повышения прежних операторов до администратора нет.
Обновляй API вместе с применением миграции: старый исполняемый код не знает новые имена ролей.

Неизменяемые снимки операций остаются исходными и могут содержать старые имена ролей.
Они поддерживаются при чтении истории и сравнении повторных запросов. Новая аутентификация
использует только четыре активные роли; исторические значения не дают возможности войти
с устаревшей ролью.

## Настройки

`npm run setup` создаёт root `.env` из примера со случайным JWT-секретом.
Существующий `.env` остаётся без изменений: недостающие настройки нужно добавить явно.
Корневой `.env` используется локальным запуском и Docker Compose, в Git он не входит.

| Переменная | Назначение |
| --- | --- |
| `COMPOSE_PROJECT_NAME` | Имя установки Compose и её томов; по умолчанию `jwx-framework`. |
| `APP_PORT`, `DATABASE_PORT` | Порты Docker на `127.0.0.1`, по умолчанию `3400` и `5547`. |
| `DATABASE_URL` | PostgreSQL для локального backend; Docker использует адрес сервиса БД. |
| `JWT_SECRET` | Обязательный случайный секрет подписи, минимум 32 байта. |
| `JWT_TTL_SECONDS` | Срок сессии, по умолчанию `3600`; допустимо от `60` до `86400`. |
| `APP_ORIGIN` | Публичный origin приложения, например `http://localhost:3400`. |
| `AUTH_ALLOWED_ORIGINS` | Дополнительные явно разрешённые origins через запятую, например Vite `http://localhost:5173`. |
| `COOKIE_SECURE` | `true` для HTTPS; локальный HTTP использует `false`. |

Origin включает схему, host и порт, но не путь.
При переносе на другой порт или домен обнови конфигурацию origin вместе с внешним адресом.
На HTTPS-развёртывании установи `APP_ORIGIN=https://...` и `COOKIE_SECURE=true`.
Не добавляй произвольные origins или wildcard, чтобы временно устранить ошибку входа.
При смене JWT-секрета ранее выданные токены перестанут проходить проверку.

## HTTP-контракт

| Запрос | Результат |
| --- | --- |
| `POST /api/auth/login` | Тело `{ email, password }`; ответ `{ user, expiresAt }` и cookie. |
| `GET /api/auth/me` | Текущий пользователь `{ user }`; без действующей сессии — 401. |
| `POST /api/auth/logout` | Отзыв текущей сессии, удаление cookie, ответ 204. |

Публичный `user` содержит `id`, `email`, `name`, `role`.
Email и пароль не передаются в query-параметрах.
Клиентский HTTP-транспорт автоматически добавляет `X-Requested-With: XMLHttpRequest`.
Он обязателен для входа и изменяющих запросов, использующих cookie.
Переданный `Origin` у изменяющего запроса должен входить в разрешённый список.
Изменяющие browser-запросы с `Sec-Fetch-Site: cross-site` также отклоняются.
Эти условия проверяются на сервере, включая login, а не только Vue Router.

Cookie применяется ко всем API-доменам. Поэтому после входа в клиент на
`http://localhost:3400` Swagger на том же origin может вызывать защищённые маршруты.
Для изменяющих запросов Swagger также передаёт обязательный заголовок.
Вход на dev-клиенте 5173 предназначен для запросов через его Vite proxy;
при использовании другого origin учитывай настройки cookie и список разрешений.

## Сессии и границы ответственности

Подпись JWT не отменяет проверку сессии в БД. На каждом защищённом запросе сервер
проверяет, что сессия существует, не истекла и не отозвана, а пользователь активен.
Актуальная роль берётся из пользователя: сохранённый JWT не закрепляет старые права.
Logout отзывает сессию, поэтому скопированный токен не продолжает работать после выхода.

Пароль хранится как scrypt-хеш со случайной солью; исходное значение не сохраняется.
HTTP-слой отвечает за cookie, проверку токена и построение Actor.
Сервисы получают обычные типизированные данные; проверки конкретной операции и владения
сохраняются в сервисах, даже если вызов пришёл из другого домена, а не из HTTP.

JWT проверяется с алгоритмом HS256, обязательным сроком действия, issuer `jwx-framework`
и audience `jwx-framework-client`. Смена формата токена требует согласованного изменения
выдачи и проверки, а не отключения проверок.

Сейчас предусмотрены вход, выход, восстановление текущего пользователя и административное
создание учётной записи. Публичная регистрация, сброс пароля по email, MFA, управление
пользователями через интерфейс и refresh-сессии не реализованы.
