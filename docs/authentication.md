# Регистрация и вход по JWT

Пользователь регистрируется сам или входит по email и паролю. Сервер создаёт сессию в БД
и выдаёт JWT в cookie `framework_session`. Сам JWT не возвращается в JSON и не хранится в localStorage.

Cookie имеет `HttpOnly`, `SameSite=Lax`, `Path=/api`; `Secure` включается для HTTPS.
По умолчанию сессия живёт один час. Refresh-токена и автоматического продления нет:
когда срок истёк, пользователь входит снова.

## Регистрация

`POST /api/auth/register` с телом `{ email, name, password }` создаёт пользователя с ролью `user`
и сразу открывает сессию (ответ 201, как у входа). Правила:

- email нормализуется (обрезка пробелов, нижний регистр), повторный email даёт 409;
- пароль от 12 до 128 символов, имя от 1 до 120 символов;
- роль из тела запроса не принимается: лишние поля отклоняются схемой (400);
- маршрут ограничен 5 запросами в минуту с одного IP и защищён теми же проверками
  Origin/CSRF, что и вход.

На клиенте регистрация доступна на `/register`, вход — на `/login`.

## Администратор

Администратора через HTTP не создать, только через CLI:

```bash
# локально, из корня
npm --prefix server run build
npm run user:create -- --email admin@example.com --name Admin --role admin

# в Docker
docker compose exec api npm run user:create -- --email admin@example.com --name Admin --role admin
```

Команда запрашивает пароль без отображения в терминале. Как аргумент CLI или через
переменную окружения пароль не принимается. Для автоматизации можно передать одну строку
через stdin. Без `--role` CLI создаёт `user`.

## Роли и middleware в маршрутах

Ролей две, они объявлены в [core/roles.ts](../server/framework/core/roles.ts):

| Роль | Кто это |
| --- | --- |
| `user` | Обычный пользователь: свои вакансии, подачи, вопросы и банк ответов. |
| `admin` | То же плюс административные маршруты, когда они появятся. |

Отсутствие входа означает отсутствие актора, отдельной роли для него нет.

| Middleware | Кто допускается |
| --- | --- |
| [publicAccess](../server/middlewares/publicAccess.ts) | Любой посетитель, включая анонимного. |
| [authenticatedAccess](../server/middlewares/authenticatedAccess.ts) | Любая действующая сессия. |
| [adminAccess](../server/middlewares/adminAccess.ts) | Только `admin`. |
| [rolesAccess(...roles)](../server/middlewares/rolesAccess.ts) | Только явно перечисленные роли. |

Middleware подключается обычным импортом в доменном `*Routes.ts` через `preHandler`:

```ts
import { authenticatedAccess } from '../../middlewares/authenticatedAccess.js';

server.get('/api/jobs', { preHandler: authenticatedAccess, schema: { /* … */ } }, controller.list);
```

Без сессии защищённый маршрут отвечает `401`, с сессией, но неподходящей ролью — `403`.
`publicAccess` помечает маршрут публичным, но общие проверки Origin, CSRF и лимиты частоты
продолжают действовать.

**Роль не заменяет проверку владельца.** Почти все данные приложения принадлежат пользователю
(`jobs.userId`, `answers.userId`). Сервис получает `Actor` и сам фильтрует и проверяет записи
по `actor.id`. Чужая вакансия должна давать 404, а не 403, чтобы не раскрывать, что она существует.
Middleware проверяет только факт входа.

## HTTP-контракт

| Запрос | Результат |
| --- | --- |
| `POST /api/auth/register` | Тело `{ email, name, password }`; ответ 201 `{ user, expiresAt }` и cookie. |
| `POST /api/auth/login` | Тело `{ email, password }`; ответ `{ user, expiresAt }` и cookie. |
| `GET /api/auth/me` | Текущий пользователь `{ user }`; без действующей сессии — 401. |
| `POST /api/auth/logout` | Отзыв текущей сессии, удаление cookie, ответ 204. |

Публичный `user` содержит `id`, `email`, `name`, `role`.
Неверный пароль и несуществующий email дают одинаковый ответ 401.
Вход ограничен 10 попытками в минуту с одного IP.

Клиентский транспорт `request` автоматически добавляет `X-Requested-With: XMLHttpRequest`.
Этот заголовок обязателен для register, login, logout и всех изменяющих запросов с cookie.
`Origin` изменяющего запроса должен входить в разрешённый список, а запросы с
`Sec-Fetch-Site: cross-site` отклоняются. Всё это проверяется на сервере.

## Настройки

| Переменная | Назначение |
| --- | --- |
| `JWT_SECRET` | Обязательный случайный секрет подписи, минимум 32 байта. |
| `JWT_TTL_SECONDS` | Срок сессии, по умолчанию `3600`; допустимо от `60` до `86400`. |
| `APP_ORIGIN` | Публичный origin приложения, например `http://localhost:3400`. |
| `AUTH_ALLOWED_ORIGINS` | Дополнительные разрешённые origins через запятую, например Vite `http://localhost:5173`. |
| `COOKIE_SECURE` | `true` для HTTPS; локальный HTTP использует `false`. |

Origin включает схему, хост и порт, но не путь. Для HTTPS задай `APP_ORIGIN=https://...`
и `COOKIE_SECURE=true`. Не добавляй wildcard, чтобы обойти ошибку входа. После смены
JWT-секрета ранее выданные токены перестают проходить проверку.

## Сессии

Подписи JWT недостаточно: на каждом запросе сервер проверяет, что сессия есть в БД,
не истекла и не отозвана, а пользователь не отключён (`disabled`). Роль берётся из текущей
записи пользователя, поэтому сохранённый JWT старые права не закрепляет. Logout удаляет сессию,
и скопированный токен сразу перестаёт работать.

Пароль хранится как scrypt-хеш со случайной солью. JWT проверяется с алгоритмом HS256,
обязательным сроком действия, issuer `jwx-framework` и audience `jwx-framework-client`.

Не реализованы: сброс пароля по email, подтверждение email, MFA, управление
пользователями через интерфейс, refresh-сессии.
