# План: модульный сборщик вакансий (этап 1 «Сбор»)

Статус: **план**, кода сборщика ещё нет. Готовы вход/регистрация и [домен `jobs`](jobs.md):
сборщик пишет через `JobService.recordFound` и проверяет новизну через `JobService.unknownUrls`.

## Цель

Один скрипт `npm run collect` выполняет поиски каждого пользователя на включённых источниках
(LinkedIn, Djinni, Indeed, …), складывает вакансии в его выдачу в `jobs` со статусом `found`
и не создаёт дублей.
Новый сайт добавляется отдельным модулем, ядро при этом не меняется.

## Устройство

```
server/
  collector/
    collect.ts              CLI: npm run collect [-- --user me@x.com --source linkedin --dry-run]
    CollectorRunner.ts      обход источников, изоляция ошибок, лимиты, итоговая статистика
    SourceTypes.ts          контракт модуля: JobSource, JobCard, SourceContext
    sources.ts              явный реестр модулей, по одной строке на источник
    http.ts / browser.ts    общие fetch-клиент и Playwright (ленивый запуск, профили)
    sources/
      linkedin/
        LinkedinSource.ts   поиск и навигация
        LinkedinParser.ts   чистый разбор HTML/JSON → JobCard (без I/O)
        README.md           инструкции: вход, лимиты, антибот, известные поломки
        fixtures/           сохранённые страницы для тестов парсера
      djinni/ …
      indeed/ …
  src/jobs/                 домен (готов): recordFound(ownerId, jobs) → { created, duplicates, invalid, jobIds }
  src/searches/             домен: поиски пользователя (источник, запрос, локация, фильтры)
```

Сборщик — отдельная точка входа рядом с `scripts/`, как `user:create`. В БД он пишет только
через `JobService` домена `jobs`, без прямого Prisma. Так ядро не зависит от того,
откуда пришли данные.

## Контракт модуля

```ts
export interface JobSource {
  id: string;                         // 'linkedin' → jobs.source
  title: string;
  /** Как модуль получает данные; от этого зависит, запускать ли браузер. */
  transport: 'api' | 'html' | 'browser';
  /** Нужен ли вход (сохранённый профиль браузера в .local/profiles/<id>). */
  requiresLogin: boolean;
  limits: { pageDelayMs: [min: number, max: number]; maxPagesPerQuery: number };

  /** Список вакансий по одному поисковому запросу; страницы отдаются потоком. */
  search(context: SourceContext, query: SearchQuery): AsyncIterable<JobCard[]>;
  /** Полный текст описания, если в списке его нет. */
  details?(context: SourceContext, card: JobCard): Promise<JobDetails>;
  /** Каноничный URL без трекинга (utm, refId, …): это ключ дедупликации. */
  canonicalUrl(url: string): string;
}

export type JobCard = {
  url: string; externalId?: string; title: string; company: string;
  location?: string; postedAt?: Date; description?: string; raw?: unknown;
};

export type SourceContext = {
  http: HttpClient;                   // ретраи, таймауты, User-Agent
  browser(): Promise<BrowserPage>;    // Playwright поднимается только по требованию
  /** Известна ли вакансия текущему пользователю; ядро реализует через JobService.unknownUrls. */
  isKnown(url: string): Promise<boolean>;
  log: Logger; signal: AbortSignal;
};
```

`JobCard` по полям совпадает с `JobInput` из `server/src/jobs/JobService.ts`: ядро передаёт
карточки в `JobService.recordFound` без преобразований и добавляет только `source` модуля.

Модуль подключается явной строкой в `sources.ts`. Динамической загрузки папок не будет:
так сохраняются автокомплит и проверка типов, и это соответствует правилам проекта
(«без динамического DI»).

## Что делает ядро (модуль об этом не думает)

1. Берёт активных пользователей (или одного, если передан `--user`) и их поиски из таблицы
   `searches`: источник, запрос, локация, фильтры, включён ли поиск. Модуль про пользователей
   не знает, он получает `SearchQuery`, а пишет в БД ядро, от имени владельца поиска.
2. Запускает источники по очереди. Ошибка одного источника записывается в отчёт,
   остальные продолжают работу.
3. Дедуплицирует внутри выдачи пользователя: `canonicalUrl` → уникальный `(userId, url)`
   и `(userId, source, externalId)`. Если у двух пользователей совпадает поисковый запрос,
   страница выдачи загружается один раз, а записи создаются каждому.
   Когда страница выдачи целиком состоит из уже известных вакансий, листание останавливается.
   Этим держится дешёвый ежедневный прогон.
4. Догружает `details()` только для новых вакансий.
5. Соблюдает паузы и лимиты страниц, ставит общий таймаут на прогон (окно ~1 час) и корректно
   останавливается по SIGINT.
6. Выдаёт итог по пользователю и источнику: страницы, найдено, новых, дублей, ошибки.
   Позже итог сохраняется в таблицу `collector_runs` и уходит пользователю в Telegram-отчёт.

## Три типа модулей

| Тип | Когда | Примеры | Цена поддержки |
|-----|-------|---------|----------------|
| `api` | у сайта есть JSON/RSS/публичный API | Greenhouse и Lever (публичные board API), RemoteOK, RSS Djinni | низкая |
| `html` | серверный HTML без JS | многие небольшие доски | средняя |
| `browser` | JS-рендер, вход, антибот | LinkedIn, Indeed | высокая: селекторы ломаются |

Правило: модуль берёт самый дешёвый транспорт, который работает. Сначала API, потом HTML,
в последнюю очередь браузер.

## Инструкции модуля

В `README.md` каждого модуля описано: как один раз войти (`npm run collect:login -- linkedin --user me@x.com`
открывает видимый браузер, профиль сохраняется в игнорируемой `.local/profiles/<userId>/<source>/`), какие URL
поиска поддерживаются, лимиты и признаки блокировки, дата последней проверки селекторов.
Для этапа «Подача» в той же папке потом появится `apply.md`: подсказки агенту по формам
этого сайта.

## Проверки

- Парсер каждого модуля — чистая функция, которую тестируют на `fixtures/` без сети.
- Общий контрактный тест проходит по всем модулям из реестра: id уникален, `canonicalUrl`
  идемпотентен и убирает трекинг, парсер на фикстуре возвращает непустые карточки.
- Тест ядра на фейковом источнике проверяет дедуп, остановку на известных вакансиях,
  изоляцию ошибок и лимиты. Отдельно проверяется, что выдачи двух пользователей не смешиваются.
- Живой прогон: `npm run collect -- --source X --dry-run` печатает карточки и ничего не пишет.

## Порядок работ

1. Домен `searches` (CRUD своих поисков) и страница «Вакансии» поверх готового `jobs`.
2. Ядро: `SourceTypes`, `CollectorRunner`, CLI, фейковый источник и тесты.
3. Первый модуль без входа (API или HTML), чтобы проверить весь путь до БД и UI.
4. LinkedIn: Playwright, сохранённый профиль, медленный темп, фикстуры.
5. `collector_runs` и systemd timer.
6. Следующие модули по одному: Djinni, Indeed, …

## Открытые вопросы

- С каких 2–3 сайтов начать?
- Нужна ли фильтрация (стоп-слова, локация, зарплата) уже на этапе сбора или только на этапе отбора?
- Вход на сайты с логином: у каждого пользователя свой профиль браузера, поэтому сборщик
  с такими источниками должен работать на машине, где пользователь один раз вошёл.
