# Пример приложения: Vodogon

Рабочий пример приёма показаний и ручных операций Vodogon с доменами `subscribers`, `readings`
и `transactions`.
Fastify 5, Prisma **7.10**, TypeScript в строгом режиме, PostgreSQL 17.

Принятые решения о структуре, нейминге, DI, границах доменов и читаемом бизнес-слое собраны в
[руководстве по архитектуре](../architecture.md). Краткие инструкции для работы с кодом —
в [AGENTS.md](../../AGENTS.md).

## Что относится только к этому примеру

Платежи, показания, тарифы, лицевые счета, финансовый журнал и правила отмены принадлежат
этому приложению. Они не задают модель данных, роли или обязательные механизмы универсального
фреймворка. Копировать их в новый проект по умолчанию не требуется.

В текущем прототипе часть прикладной интеграции ещё размещена рядом с общей основой:

- [core/actor.ts](../../server/framework/core/actor.ts) содержит контекст с ролью приложения,
  необязательный `subscriberId` и проверку доступа абонента. Активные роли admin/manager/guest/foreign
  объявлены в [core/roles.ts](../../server/framework/core/roles.ts). Связь с лицевым счётом относится
  к демонстрации; выделение общей модели контекста и прикладных политик ещё предстоит.
- [create-application.ts](../../server/framework/composition/create-application.ts) и
  [регистрация маршрутов](../../server/framework/composition/register-domain-routes.ts) связывают конкретные
  домены демо. Состав приложения определяет сам проект.
- [UoW операций](../../server/framework/composition/prisma-transaction-unit-of-work.ts) блокирует абонента,
  а [UoW показаний](../../server/framework/composition/prisma-reading-unit-of-work.ts) связывает конкретные
  возможности записи. Перенос ранее записанной истории также относится только к демо.
- [Middleware generalAccess](../../server/middlewares/generalAccess.ts) допускает admin/manager,
  [guestAccess](../../server/middlewares/guestAccess.ts) также допускает guest.
  Доменные сервисы дополнительно проверяют доступ к лицевому счёту.
  Вход выполняется через JWT и сохранённые сессии; статические demo-токены удалены.
- Схема Prisma и сгенерированный клиент описывают данные этого приложения. Новое приложение
  определяет собственные модели и миграции.

Общими остаются принципы явного DI, границ доменов, читаемых правил и подключения инфраструктуры.
Эта документация описывает работающий пример; она не делает полный перенос Vodogon задачей
развития фреймворка. Команды ниже выполняются из корня репозитория;
дерево серверных файлов и короткие пути внутри него указаны относительно `server`.

Ниже «оператор» обозначает предметную функцию сотрудника с ролью `admin` или `manager`,
а «абонент» — `guest`, связанный с нужным счётом через `subscriberId`.
Гость без такой связи не получает доступ к лицевым счетам; foreign не получает доступ
к предметным операциям. Это правила примера, не обязательные правила всех доменов.

## Вызвать пример

Запуск и создание пользователя описаны в [README](../../README.md).
Основной Vue-клиент показывает универсальный пример задач и вход по JWT.
Старые HTML-экраны показаний и операций заменены этим клиентом;
домены Vodogon продолжают работать через API и [Swagger](http://localhost:3400/docs).
Войди оператором в клиент на том же origin перед вызовом защищённых маршрутов.

Для первого абонента `demo-subscriber-1` начальные данные: **1501.83 м³**,
тарифы **10 + 2 грн/м³**, баланс **−50 грн**.
Preview показания **1511.00** даёт **9.17 м³**, начисление **110.04 грн**
и баланс после сохранения **−160.04 грн**. Сохранение действительно меняет демонстрационную БД.
При повторных проверках используй актуальное состояние карточки: seed его не сбрасывает.

Второй абонент подключён только к воде. У третьего выключены обе услуги:
показание можно передать с нулевым начислением, как в выбранном legacy-сценарии.
Для проверки доступа абонента создай отдельного пользователя с ролью `guest`
и `subscriberId` первого счёта через [команду создания пользователя](../authentication.md).

Для операций есть отдельный вымышленный счёт **DEMO-004** (`demo-subscriber-4`):
начальное показание **100 м³**, тарифы **30 + 15 грн/м³**, баланс воды **−100 грн**,
баланс обслуживания **−15 грн**. Оплата **40 грн** сначала закрывает долг обслуживания:
**15 грн** идут на обслуживание, **25 грн** — на воду. Получаются балансы **−75 грн** и **0 грн**.
Описанные суммы относятся к новому счёту; существующая история не удаляется.

Все имена, лицевые счета и тарифы вымышленные. Существующие БД и сервисы Vodogon не используются.
Новый вход не выдаёт общие токены и не позволяет переключить роль без другой учётной записи.
Docker публикует порты только на `127.0.0.1`, повторный запуск сохраняет том PostgreSQL.

```bash
docker compose logs -f api
docker compose down
```

Не добавляй `-v`, если нужна введённая история. Параметры портов и окружения находятся
в root `.env.example` и [README](../../README.md); при изменении адреса обнови `APP_ORIGIN`.

## С чего читать код примера

1. [Читаемый расчёт](../../server/src/readings/ReadingRules.ts) — сами шаги бизнес-правила.
2. [Сценарий сохранения](../../server/src/readings/ReadingService.ts) — доступ, повтор запроса,
   загрузка данных, расчёт и атомарная запись.
3. [Сборка зависимостей](../../server/framework/composition/create-application.ts) — явный DI без строкового контейнера,
   `Object.assign`, декораторов классов и глобальных экземпляров.
4. [Транзакция между доменами](../../server/framework/composition/prisma-reading-unit-of-work.ts) — обе реализации
   репозиториев получают один Prisma transaction; сервисы видят обычные TypeScript-интерфейсы.
5. [Контроллер](../../server/src/readings/ReadingController.ts) — только HTTP-вход и вызов сервиса;
   [маршруты и их JSON-схемы](../../server/src/readings/ReadingRoutes.ts) находятся в одном файле домена.
6. [Общий доступ сотрудников](../../server/middlewares/generalAccess.ts),
   [доступ гостя](../../server/middlewares/guestAccess.ts) и [инфраструктурный плагин](../../server/plugins/infrastructure.ts).
7. [Правила операций Vodogon](../../server/src/transactions/TransactionRules.ts) — распределение платежа,
   показания, сверка, отмена и изменение описания; [сервис](../../server/src/transactions/TransactionService.ts)
   отвечает за доступ, версии, повторы и атомарное сохранение.

```ts
reading.ensureGreaterThan(previous);
const consumption = reading.consumptionSince(previous);
const charge = consumption.chargedAt(tariff);
const balanceAfterCharge = balance.afterCharge(charge);
```

Подготовка показаний и баланса из входных данных, а также сборка полей результата находятся в
[ReadingCalculationData.ts](../../server/src/readings/ReadingCalculationData.ts). В `ReadingRules.ts` остаются
выбор тарифа по подключённым услугам, проверка увеличения показания и шаги расчёта.
Реализация арифметики находится в небольших объектах `MeterReading`, `WaterConsumption`, `WaterTariff`,
`Money`, `AccountBalance`. Подготовка данных и бизнес-правила не зависят от Prisma или Fastify
и не выполняют скрытых запросов к БД.
Автокомплит работает через обычные типы конструкторов; никаких расширений редактора не нужно.

В `src` находятся только домены. Внутри домена файлы лежат рядом, а назначение видно по имени:
`SubscriberService`, `SubscriberController`, `SubscriberRepository` — как в zijn-crm.
Публичные типы и интерфейс сервиса находятся в `*Types.ts`: через эти файлы другие домены
получают доступ к контракту. Внутренние интерфейсы репозитория и транзакций остаются в `*Contracts.ts`.
Каждый домен хранит HTTP-маршруты и их JSON-схемы в своём файле `*Routes.ts`, без отдельного файла схем;
[сборка маршрутов](../../server/framework/composition/register-domain-routes.ts) подключает их к приложению.
Общие технические маршруты находятся в [плагине](../../server/plugins/system-routes.ts).
Домен `transactions` следует тем же правилам: плоская структура, публичная граница в
`TransactionTypes.ts`, внутренние интерфейсы в `TransactionContracts.ts`, схемы в `TransactionRoutes.ts`.
Преобразования чисел и сборка объектов результата вынесены из `TransactionRules.ts` в
`TransactionCalculationData.ts` и `TransactionAmount.ts`.

Контроллеры получают только публичные API. Сервисы используют собственные репозитории и публичные API
других доменов. Обычный `SubscriberApi` предоставляет только чтение; в его типе нет метода изменения
показания или баланса. Для сохранения `ReadingService` получает отдельную возможность
`SubscriberMeterStateWriter` только внутри `ReadingUnitOfWork`: сборка передаёт её вместе с репозиторием
истории в одной транзакции. Это контракт домена абонентов, без доступа к его репозиторию.
Зависимости явно объявлены в типизированных конструкторах и передаются при сборке приложения;
обычные импорты и автокомплит сохраняются. Prisma-типы остаются в репозиториях, преобразователе снимков
и сборке. Полный объект Fastify в сервисы не передаётся.

`npm --prefix server run architecture` проверяет импорты через AST TypeScript, включая алиасы, реэкспорты и динамические
импорты. Роль модуля определяется по имени файла, а не по технической подпапке. Запрещены чужие
внутренние модули, репозитории из контроллеров и инфраструктура в бизнес-правилах. Предметные объекты
по умолчанию считаются чистыми и тоже не могут импортировать Fastify, Prisma или репозитории.
Проверка запускается и при сборке Docker. Это проверка архитектуры исходного кода, не изоляция
недоверенного кода в одном Node.js-процессе.

## Правила примера `readings`

Основание: legacy `../vodogon/api.vodogon-keg.com/controllers/Transactions.php`
(`add_cubes`, `add_cubes_safe`, расчёт включённых тарифов) и `../vodogon/docs/agents/billing.md`.
`vodogon-next` источником правил не использовался.

- Показание нормализуется до двух знаков, HALF_UP. Точный исходный ввод сохраняется.
- Новое нормализованное показание должно быть больше предыдущего.
- В `readings` уменьшение и замена счётчика не разрешены. Ручное уменьшение оператором
  реализовано отдельно в `transactions`; замена счётчика требует собственного сценария.
- Учитывается сумма тарифов только включённых услуг.
- Расход умножается на **суммарный тариф**, затем сумма округляется один раз до копеек.
- Начисление вычитается из баланса. Отрицательный баланс — задолженность.
- Выключение обеих услуг даёт нулевое начисление и допускает увеличение показания.

В API суммы представлены целыми копейками, объёмы — целыми сотыми м³. Внутреннее умножение использует
`BigInt`, без ошибок двоичной дробной арифметики. Предельные значения явно проверяются.

## Сохранение и история

Предварительный расчёт ничего не пишет. Для сохранения нужны `expectedVersion` из расчёта и заголовок
`Idempotency-Key`. Данные перечитываются внутри транзакции. Версия защищает от сохранения устаревшего
расчёта и параллельного изменения карточки. При конфликте API отвечает `409`, нужно пересчитать.

Повтор того же ключа с тем же вводом и актором возвращает ту же операцию без второго начисления.
Другой ввод или актор с тем же ключом — `409`. Два запроса с разными ключами и одной версией не могут
оба изменить карточку. Обновление абонента и запись истории либо сохраняются вместе, либо откатываются.

История содержит ID операции, ключ, точный ввод, актора, источник, время, версию правила,
снимок абонента и тарифов, показания/баланс до и после, расход и начисление.
Записи нельзя изменить или удалить через репозиторий; PostgreSQL-триггер также блокирует UPDATE/DELETE.
Исходные записи показаний остаются свидетельством расчёта. Отмена ручных операций и представление
исправленной истории описаны ниже для домена `transactions`.
Миграция ролей не переписывает эти снимки: старые operator/subscriber остаются читаемыми
историческими значениями. При проверке повторного запроса они сопоставляются с manager/guest;
активные пользователи и новые записи используют текущие роли приложения.

## Перенос ручных операций Vodogon

Источник правил — legacy-файлы соседнего проекта `../vodogon/api.vodogon-keg.com`:
`controllers/Transactions.php`, `src/api.php`,
`tests/Integration/TransactionsBusinessTest.php` и
`tests/Integration/TransactionDeletionBusinessTest.php`.
Они не входят в этот репозиторий и не требуются для его запуска.
`vodogon-next` источником не является. Перенесены сценарии ручного журнала; имена HTTP-маршрутов
и JSON-контракт новые, совместимость со старым PHP API не заявляется.

| Операция legacy | Новый сценарий | Поведение |
| --- | --- | --- |
| `add_balance`, `add_balance_bank`, учёт импортированного платежа | `kind: "payment"` | Положительная сумма с точностью до копейки. Сначала закрывается отрицательный баланс обслуживания, остаток зачисляется на воду. Для банка обязательна `externalReference`, необязательное `purpose` сохраняется. |
| `add_cubes` | `kind: "reading"`, оператор | Ненулевое изменившееся показание; оператор может уменьшить его с возвратом начисления по включённым тарифам. `verified: true` делает показание контрольным. |
| `add_cubes_safe` | `kind: "reading"`, абонент | Только собственный счёт, строгое увеличение после округления, без права подтвердить контрольное показание. |
| `create_fast` | `kind: "reconciliation"` | Оператор задаёт абсолютные целевые балансы воды и обслуживания и показание, с обязательной причиной. Рассчитываются разницы с текущими значениями. Подтверждение показания меняется только при его изменении. |
| Создание записи без движения состояния | `kind: "note"` | Обязательный текст, без движения денег, показания или подтверждения. |
| `update` описания | `amendDescription` | Новое описание и причина записываются отдельным событием; исходный текст и расчёт сохраняются. Прямого редактирования финансовых полей нет. |
| `delete` обычной операции | `cancel` | Исходные изменения вычитаются из текущего состояния; создаётся связанная запись отмены. Последующие платежи не теряются. |

Сумма платежа `40.00` допустима, `40.001` отклоняется: платёж не округляется до копеек.
Показания и целевые балансы сверки нормализуются до сотых с HALF_UP; начисление округляется
один раз после умножения расхода на сумму включённых тарифов. В JSON-ответах суммы — целые копейки,
показания — целые сотые м³. Банковский идентификатор проверяется на повторный учёт в пределах счёта;
новый ключ HTTP-запроса сам по себе не позволяет учесть тот же банковский платёж снова.

Оператор выполняет платежи, сверки, заметки, изменение описания, отмену и экспорт.
Абонент видит только свою историю и передаёт только свои возрастающие показания. Проверки выполняются
и в сервисе/правилах, а не только в HTTP middleware. Для сохранения, отмены и изменения описания нужны
текущая `expectedVersion` карточки и `Idempotency-Key`; повтор того же запроса возвращает сохранённый
результат. Изменение карточки и запись журнала выполняются в одной транзакции.

Каждая запись хранит исходный запрос, актора, снимок абонента, тарифы, изменения, состояния до/после
и сведения о подтверждении показания. Ссылки `reversesId` и `amendsId` связывают отмены и исправления
с оригиналом. В отличие от физического удаления legacy, исходные свидетельства не удаляются.
Представление истории содержит актуальное описание, `cancelledBy` и пересчитанные `projection.before/after`
для последующих операций; `record.effect` сохраняет снимок на момент исходного выполнения.

API показаний тоже записывает операцию в этот журнал, в одной транзакции с начислением.
При запуске seed добавляет в журнал ранее сохранённые демонстрационные показания, используя их
исходные снимки. Повторный запуск не меняет баланс и не создаёт дубликаты; таблица показаний сохраняется.

Например, после оплаты 40 грн на DEMO-004 балансы равны −75/0. Ещё одна оплата 20 грн даёт −55/0.
Отмена первой оплаты вычитает её исходные 25/15 из текущих балансов: получится **−80/−15**,
а вторая оплата останется учтённой. При отмене контрольного показания восстанавливается подходящее
действующее подтверждение из истории. Это отмена поддержанных операций с сохранением доказательств,
не универсальный откат любого состояния базы.

Журнал и карточку операции можно читать через `GET /api/transactions` и `GET /api/transactions/:id`.
Фильтры: `subscriberId`, `kind`, `from`, `to`, `search`; порядок и страницы — `order`, `page`, `limit`.
Поиск учитывает лицевой счёт, имя, описание, банковский идентификатор и назначение платежа.
`GET /api/transactions/export.csv` выгружает все подходящие записи независимо от страницы
(до 10 000 записей), с теми же фильтрами. Это CSV-экспорт нового журнала; старый универсальный
`/transactions/export/:type` не воспроизведён.

Для создания доступны `POST /api/transactions/preview` без сохранения и `POST /api/transactions`.
Пример тела оплаты для нового DEMO-004; если карточка уже изменялась, подставь её текущую версию:

```json
{
  "kind": "payment",
  "subscriberId": "demo-subscriber-4",
  "expectedVersion": 0,
  "amount": "40.00",
  "method": "cash"
}
```

Отмена — `POST /api/transactions/:id/cancel` с `expectedVersion` и `reason`.
Изменение описания — `PATCH /api/transactions/:id/description` с `expectedVersion`, `description`
и `reason`. Полные схемы находятся в Swagger и `TransactionRoutes.ts`.

Проверки перенесённых правил описаны в [transactions-business.test.ts](../../server/tests/transactions-business.test.ts),
представления истории и восстановления подтверждений — в
[transactions-history.test.ts](../../server/tests/transactions-history.test.ts). Эти проверки не заменяют
отдельную миграцию и сверку реальных данных Vodogon.
Проверки HTTP, PostgreSQL, конкурентных запросов и сохранения истории находятся в
[transactions-integration.test.ts](../../server/tests/transactions-integration.test.ts).

В этот перенос не входят месячные начисления, запуск начисления обслуживания, замена счётчика
и смена владельца, банковские парсеры файлов и webhooks, внешние XLS/XML-экспорты.
Их внутренние типы нельзя создать через ручной API. Операции обслуживания и замены счётчика
нельзя отменять общей командой; отмена более ранней операции также блокируется, если после неё
есть действующее начисление или перенос обслуживания. Эти случаи требуют отдельных сценариев
соответствующих доменов. Исторические repair-функции, маршруты которых в legacy были закомментированы,
не перенесены. Данные production и существующая БД Vodogon не мигрируются и не изменяются.

## Вызвать API

Войди оператором через [клиент](http://localhost:3400), затем открой
[Swagger](http://localhost:3400/docs) на том же origin: он использует установленную cookie.
Статические `demo-operator-token` и `demo-subscriber-token` больше не работают.

Для `POST /api/readings/preview` передай тело:

```json
{
  "subscriberId": "demo-subscriber-1",
  "reading": "1511.00"
}
```

Для `POST /api/readings` добавь `expectedVersion` из актуального
`calculation.subscriberVersion` preview и уникальный заголовок `Idempotency-Key`.
Если показание уже превышает 1511.00, выбери новое значение, превышающее текущее.
JWT-сессия не меняет правила версии, идемпотентности и доступа к счёту.

## Локальная разработка и проверки

Общие команды установки, запуска и настройки отдельной тестовой БД находятся в
[README](../../README.md#локальная-разработка).

```bash
npm run check:server
```

Команда проверяет актуальность генерации, TypeScript, границы импортов, бизнес-правила и сборку.
Интеграционные тесты требуют отдельной PostgreSQL-БД и явно заданного `TEST_DATABASE_URL`;
без неё они пропускаются. Они добавляют тестовые записи, не очищая рабочую историю.
Для установки зависимостей используется `server/package-lock.json`.
Точечные overrides обновляют транзитивные `deepmerge-ts` и `mysql2` в инструментах Prisma 7.

Этот пример показывает приём показаний и ручной журнал операций. Полного переноса остальных
доменов, тарифной истории и периодов начисления здесь нет.
Их реализация не является обязательным этапом развития универсального фреймворка.
