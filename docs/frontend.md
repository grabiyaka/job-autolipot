# Клиент: Vue Options API и SCSS

Клиент расположен в `client`. Принятые соглашения:
страницы рядом с компонентами своей сущности, Options API, вложенный SCSS и адаптивность
внутри изменяемого селектора. Серверные домены и клиентские компоненты развиваются отдельно.

## Структура

```text
client/
  src/
    components/
      jobs/                  страница вакансий
      user/                  вход и профиль
      ui/                    общие элементы интерфейса
    store/user.ts            состояние пользователя и сессии
    router/index.ts          маршруты и восстановление входа
    mixin/fetch.ts           типизированный HTTP-транспорт
    assets/css/
      common.scss            общие переменные и responsive-миксин
      style.scss             базовые стили, поля и кнопки
    App.vue                  оболочка приложения
    main.ts                  подключение Vue, Pinia и Router
  scripts/                   проверка клиентских соглашений
  tests/
  package.json
```

Папка `mixin` хранит технические возможности клиента.
`request<T>` подключается явным импортом: транспорт не добавляет методы в компоненты
через неявные глобальные mixins. Автокомплит и зависимости видны TypeScript.

Страницы доступны по `/login`, `/register`, `/jobs` и `/profile`.
`/login` и `/register` — одна страница `LoginPage` в двух режимах. `/jobs` пока заглушка.
Новый экран добавляется в папку своей сущности, общие контролы — в `components/ui`.
Отдельная обязательная папка `pages` и дополнительные слои для каждого экрана не нужны.

## Options API и типизация

Компоненты оформляются в порядке `template`, `script`, `style`:

```vue
<template>
  <section class="project-list">
    <h1>{{ heading }}</h1>
    <p v-if="loading">Загрузка…</p>
  </section>
</template>

<script lang="ts">
import { defineComponent } from 'vue';

export default defineComponent({
  data() {
    return {
      heading: 'Проекты',
      loading: false,
    };
  },
  methods: {
    async loadProjects() {
      // Вызов типизированного API и обновление данных компонента.
    },
  },
  mounted() {
    void this.loadProjects();
  },
});
</script>

<style lang="scss" scoped>
.project-list {
  display: grid;
  gap: 16px;

  h1 {
    margin: 0;
  }
}
</style>
```

Логика компонента находится в `data`, `computed`, `methods`, `watch` и lifecycle hooks.
Не используем `<script setup>` и Composition API для логики компонентов.
`defineComponent` сохраняет типизацию `this` и не меняет Options API.

Pinia stores также описываются через `state`, `getters`, `actions`.
В компоненты состояние и методы подключаются через `mapState` / `mapActions`.
Не создаём глобальный локатор объектов или изменение прототипов ради коротких вызовов.
Имена полные и предметные: `response`, `job`, `saveAnswer`, без `resp`, `btn`, `processData`.

Публичные DTO сервера импортируются только как типы из доменных `*Types.ts`,
например `store/user.ts` берёт `UserProfile` из `server/src/users/UserTypes.ts`.
Страница вакансий будет так же брать типы из `server/src/jobs/JobService.ts` (только `import type`).
Prisma-модели, Fastify, сервисы и репозитории в клиент не импортируются.
HTTP-схемы сервера остаются проверкой внешних данных; TypeScript не валидирует JSON во время исполнения.
Типизированные UI-данные формы могут отличаться от DTO, например пустая строка вместо nullable-даты.
Такое преобразование получает понятное имя и выполняется на границе формы и запроса.

## SCSS: вложенность и общие стили

Стили компонента — `<style lang="scss" scoped>`, вложенные в его корневой класс.
Дочерние селекторы находятся внутри родительских, состояния оформляются через `&`.
Каждое свойство пишется на своей строке, отступ — два пробела.

```scss
.project-list {
  display: grid;
  gap: 20px;

  .project {
    display: flex;
    align-items: center;
    gap: 12px;

    &.archived {
      color: dimgray;
    }

    .title {
      flex: 1;
    }
  }
}
```

Цвета берутся из общих SCSS-переменных или записываются именами CSS-цветов.
Не добавляем произвольные hex-цвета в компоненты.
Общие размеры, палитра и миксины живут в `assets/css/common.scss`;
подключаем их через Sass `@use`. Файл общих переменных и миксинов сам не генерирует CSS.

Поля, подписи, кнопки и их состояния оформляются один раз в `assets/css/style.scss`
либо в соответствующем общем UI-компоненте.
На странице описываем её компоновку, а не новую копию `input`, `label` или `.button`.
Изменение общего контрола должно применяться ко всем его потребителям.
Для логических переключателей используется `BoolInput` с понятной подписью и состоянием для assistive technology.

Стили — обычный SCSS: без Tailwind, CSS-in-JS, встроенных style-атрибутов для постоянного оформления
и длинных цепочек utility-классов вместо компонента.
CSS-переменная или динамический стиль допустимы для значения, которое действительно вычисляется
во время исполнения, а не для обхода организации SCSS.

## Адаптивность рядом с элементом

`responsive($max-width)` объявлен один раз в `common.scss`.
Вызов располагается **внутри селектора, который изменяется**, рядом с обычными свойствами:

```scss
@use '@/assets/css/common.scss' as *;

.project-list {
  display: grid;
  grid-template-columns: 240px 1fr;
  gap: 24px;

  @include responsive(760px) {
    grid-template-columns: 1fr;
    gap: 16px;
  }

  .actions {
    display: flex;
    gap: 12px;

    @include responsive(480px) {
      flex-direction: column;
    }
  }
}
```

Так обычное состояние и изменение на узком экране читаются в одном месте.
Не переносим все media queries в конец файла с повторным описанием дерева селекторов.
Не поддерживаем отдельную мобильную копию DOM, если раскладку можно изменить CSS.

## Минимальная разметка и доступность

Каждая обёртка должна иметь смысл: семантика, независимая область layout или поведение.
Используем `main`, `header`, `nav`, `form`, `ul/li`, `button` и `label` по назначению.
Не добавляем несколько вложенных `div` вокруг текста ради отступа или одного цвета.
Vue-компонент сам по себе не является причиной добавлять DOM-узел.

Минимальность не отменяет подписи полей, заголовки, состояния ошибок и доступность с клавиатуры.
У кнопок действия указан `type`; формы обрабатывают `@submit.prevent`.
Ожидание блокирует повторную отправку, ошибки объясняют результат операции,
а подтверждение удаления представлено интерфейсом компонента, без нативных `alert` / `confirm` / `prompt`.

## API, сессия и маршруты

`request<T>` отправляет запросы к относительным адресам `/api/...`, передаёт cookie
и `X-Requested-With: XMLHttpRequest`, разбирает JSON и сообщает HTTP-ошибку.
Компоненты не собирают JWT-заголовки самостоятельно и не хранят секрет в browser storage.
Параметры query собираются через `URLSearchParams`.

`store/user.ts` управляет входом, получением текущего пользователя и выходом.
Router восстанавливает пользователя перед защищённой страницей.
После истечения сессии интерфейс возвращает к входу; redirect допускает только внутренний маршрут.
Ограничение маршрута улучшает интерфейс, но доступ к данным всегда проверяет сервер.

В Docker клиент и API используют один origin. В разработке Vite на `localhost:5173`
проксирует API на `localhost:3400`; разрешённый origin разработки настроен сервером явно.
Схема JWT, cookie и отзыв сессии описаны в [руководстве авторизации](authentication.md).

## Проверки

Из корня репозитория:

```bash
npm run check:client
```

Команда запускает `vue-tsc`, проверку соглашений компонентов и SCSS, тесты и Vite build.
Проверка соглашений помогает выявлять нарушения, но не доказывает читабельность,
минимальность DOM и качество адаптивной раскладки — это остаётся частью ревью.

При изменении поведения проверяем вход, выход, обновление защищённой страницы,
ошибку 401 и затронутые операции CRUD. При изменении интерфейса проверяем desktop
и узкий экран, горизонтальный скролл, видимый focus и управление клавиатурой.
