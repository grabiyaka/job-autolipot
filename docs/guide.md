# Как это работает и как этим пользоваться

Практическое руководство: что делает система, как её один раз настроить, как запускать сбор
и оценку и где смотреть результат. Как всё устроено целиком — в [overview.md](overview.md);
внутреннее устройство сборщика — в [collector-plan.md](collector-plan.md), связь с Job-Tracker —
в [trackers.md](trackers.md), запуск и проверки для разработки — в [development.md](development.md).

Состояние на 2026-11-03: **работают «Сбор» (LinkedIn) и «Отбор»** (оценка локальной qwen по профилю
из Job-Tracker и отправка отобранных в его To Apply). Подачи и Telegram ещё нет.

## 1. Общая схема

```
             ┌──────────────────────────── job-autopilot ────────────────────────────┐
 LinkedIn ──▶│ 1. Сбор          →  2. Отбор           →  3. Подача      →  4. Telegram │
 (agent      │ npm run collect     npm run score         DeepSeek + MCP    отчёт и     │
  Chromium)  │ ✅ работает          ✅ qwen по профилю JT   ⏳                вопросы ⏳   │
             └──────────────┬───────────────────┬────────────────────────────────────┘
                            ▼                   ▼  queued + оценка
             SQLite: server/data/job-autopilot.db       Job-Tracker: To Apply
             jobs · searches · search_runs ·            (профиль кандидата берётся оттуда)
             tracker_profiles · applications · …
```

Каждый этап двигает вакансию по статусам:

```
found ──▶ scored ──▶ queued ──▶ applying ──▶ applied
  │          │                     ├──▶ needs_input  (агенту нужны ответы от тебя)
  │          └──▶ rejected         └──▶ failed
  └──▶ rejected  (отсеяна фильтром по названию ещё при сборе)
```

Сейчас вакансии доходят до `queued`, `rejected` или `skipped` (повтор или уже есть в Job-Tracker).
`applying` и дальше появятся вместе с этапом 3.

## 2. Как устроен сбор

Браузер свой не запускается. Сборщик ходит через **agent Chromium** на этом сервере — тот же,
что использует Telegram-бот. Это обычный Chromium с постоянным профилем, в котором ты вошёл
в LinkedIn. Доступ к нему — через **брокер** (Unix-сокет `/run/agent-browser/broker.sock`),
который умеет только читать страницы: открыть URL, прочитать текст и ссылки, прокрутить.
Кликать, вводить и отправлять формы он не может.

Один прогон `npm run collect -- … --source linkedin --query "node.js" --location Remote`:

1. Открывает классическую выдачу `linkedin.com/jobs/search/?keywords=node.js&f_WT=2&sortBy=DD&skipRedirect=true`
   (свежие сначала; `Remote` — фильтр удалённой работы; `skipRedirect=true` не даёт LinkedIn
   увести на новый AI-поиск `/jobs/search-results/`, где нет ссылок на вакансии).
2. Ждёт, пока появятся карточки, и прокручивает список по одному экрану: после каждого шага
   читает ссылки `/jobs/view/<id>/` с названиями и добавляет новые (список виртуализирован —
   карточка появляется, только когда побывала на экране). Стоп: 25 карточек, 2 чтения подряд без
   новых или 8 шагов. Обычно набирается все 25 карточек страницы.
3. Отбрасывает вакансии, которые у тебя уже есть в базе.
4. **Фильтр по названию** (`--include`, `--exclude`): неподходящие сохраняются как `rejected`
   с причиной, их страница не открывается. Это экономит ~8 с на вакансию.
5. Каждую прошедшую открывает (пауза 4 с между вакансиями) и берёт со страницы компанию,
   локацию, описание и признак Easy Apply. Сохраняет как `found`.
6. Через 6–12 с переходит на следующую страницу выдачи (`start=25, 50, …`), всего до 4 страниц.
7. Останавливается, когда: выдача кончилась (`end`); на странице нет новых — дальше уже
   известные (`known`); дошёл до 4 страниц (`limit`); Ctrl+C или `--max-minutes` (`aborted`);
   ошибка (`error`).

Сборщик **не оценивает** вакансии и **не смотрит** на Easy Apply — он только собирает.
Easy Apply записывается как признак (`raw.easyApply`) для этапа подачи. Подаваться будем на все.

Время (оценка по паузам в коде, на живом прогоне не замерено): прокрутка страницы выдачи — до ~20 с,
каждая открытая вакансия — пауза 4 с плюс ~4–5 с на загрузку, между страницами 6–12 с. Без фильтра
это ~3,5–4 минуты на страницу из 25 вакансий и до ~15 минут на запрос (4 страницы, до 100 вакансий).
Фильтр по названию сокращает время пропорционально отсеянным: их страницы не открываются.
Второй прогон того же поиска в тот же день обычно заканчивается на первой странице (`known`).

## 3. Первый запуск (один раз)

Все команды — из корня проекта `~/projects/job-autopilot`.

```bash
npm run setup          # создаёт .env из .env.example (случайный JWT_SECRET); существующий не трогает
npm run install:all    # зависимости server и client
npm run db:generate    # Prisma Client
npm run db:migrate     # создаёт/обновляет базу; повторяй после каждого git pull с новыми миграциями
npm --prefix server run build
npm run user:create -- --email illia.herasymets@gmail.com --name Illia   # пароль спросит в терминале
```

Проверь браузер и вход в LinkedIn:

```bash
npm run browser:check                                            # брокер жив? (только чтение)
npm run browser:check -- --open https://www.linkedin.com/jobs/   # видна страница вакансий от твоего имени?
```

Во втором выводе должны быть ссылки вроде `/in/<твой-профиль>/`. Если вместо этого страница
логина — войди в LinkedIn в agent Chromium через noVNC (`http://127.0.0.1:6080` на сервере;
снаружи — через SSH-туннель или Tailscale).

### Что в `.env`

`npm run setup` заполняет почти всё сам. Для сбора и оценки важны:

| Переменная | Значение | Зачем |
|---|---|---|
| `DATABASE_URL` | `file:./data/job-autopilot.db` | база (путь относительно `server/`) |
| `AGENT_BROWSER_SOCKET` | `/run/agent-browser/broker.sock` | брокер agent Chromium |
| `OLLAMA_URL` | `http://127.0.0.1:11434` | сервер Ollama |
| `OLLAMA_MODEL` | `qwen3.5:4b` | модель для оценки |
| `OLLAMA_NUM_CTX`, `OLLAMA_TIMEOUT_MS` | `8192`, `120000` | контекст и таймаут одного запроса |
| `JOB_TRACKER_URL`, `JOB_TRACKER_TOKEN` | **заполнить вручную** | профиль кандидата и To Apply; без них `npm run score` не запускается |

Остальное (`JWT_SECRET`, `PORT`, `APP_ORIGIN`, …) нужно веб-серверу и Swagger. Полный список —
в [overview.md](overview.md#7-настройка).

### Оценка: Ollama и Job-Tracker

1. Ollama запущена (системный сервис: `systemctl status ollama` → active) и модель скачана:
   `ollama pull qwen3.5:4b` (или та, что в `OLLAMA_MODEL`).
2. В Job-Tracker заполнен профиль и создан токен:
   `npm run cli -- auth tokens create … --scopes ai:profile:read,ai:jobs:read,ai:jobs:write,ai:jobs:evaluate`
   (команда репозитория Job-Tracker). URL и токен — в `JOB_TRACKER_URL` и `JOB_TRACKER_TOKEN`.
3. Email пользователя autopilot должен совпадать с email владельца токена в JT: так пользователь
   «привязан». Проверка: `GET /api/tracker/status` → `linked: true` ([trackers.md](trackers.md)).

## 4. Ежедневное использование

### Первый полный цикл — по шагам

Как сбор переходит в оценку qwen: **никакого переключения нет, связка — статус в базе.**
Сбор пишет вакансии как `found`. Оценка (`npm run score`) берёт из базы *все* `found` этого
пользователя, включая оставшиеся с прошлых прогонов, и по одной отправляет их в Ollama
(модель из `OLLAMA_MODEL`, сейчас `qwen3.5:4b`). `npm run cycle` просто делает оба шага подряд
в одном процессе. Ollama — системный сервис, отдельно её запускать не нужно; первая вакансия идёт
~45 с (модель загружается в GPU), дальше ~14 с на каждую.

В первый раз лучше пройти по шагам и смотреть результат на каждом. Все команды — из корня проекта.

**0. Всё ли живо** (секунды):

```bash
npm run browser:check -- --open https://www.linkedin.com/jobs/   # LinkedIn залогинен
ollama list | grep qwen3.5                                       # модель скачана
npm run score -- --user illia.herasymets@gmail.com --limit 1 --dry-run   # JT отвечает, пользователь привязан
```

Последняя команда ничего не пишет. Успех — строка `профиль rev N`: профиль из JT получен. Если в базе
уже есть `found`, она заодно оценит одну вакансию, то есть проверит и Ollama; если нет — `queued 0, rejected 0…`,
и Ollama проверится на шаге 2. Ошибки — в [разделе 5](#5-если-что-то-не-так).

**1. Сбор** (~2–4 минуты): сначала с `--dry-run`, посмотреть, что отсеет фильтр по названию,
потом та же команда без него:

```bash
npm run collect -- --user illia.herasymets@gmail.com --source linkedin \
  --query "node.js" --location Remote \
  --include "node,typescript,javascript,full stack,fullstack,backend,frontend,software engineer" \
  --exclude "java,android,ios,c++,qa,data engineer,machine learning,devops,sap,abap"
```

**2. Пробная оценка** на нескольких вакансиях, без записи:

```bash
npm run score -- --user illia.herasymets@gmail.com --limit 5 --dry-run
```

Смотри на строки `+`/`−`: согласен ли ты с оценками и причинами.

**3. Оценка всех найденных**, пока без отправки в Job-Tracker (~14 с на вакансию: 50 вакансий ≈ 12 минут):

```bash
npm run score -- --user illia.herasymets@gmail.com --no-push
```

**4. Посмотреть результат** — в терминале или Swagger ([ниже](#где-смотреть-результат)). Если модель
отклонила то, на что ты подался бы, верни вакансию в `queued` (`PATCH /api/jobs/{id}`).

**5. Отправить отобранное в Job-Tracker:**

```bash
npm run score -- --user illia.herasymets@gmail.com
```

Новых `found` уже нет, поэтому оценка ничего не делает, а `queued` уходят в JT:
`Job-Tracker: отправлено N, …`. Проверь их в JT в списке **To Apply** — с оценкой, verdict и причиной.

**Дальше — одной командой.** Когда шаги выше проверены, ежедневный прогон — это `npm run cycle`
с тем же поиском (сбор → оценка → отправка), см. [ниже](#сбор-оценка-и-отправка-одной-командой--npm-run-cycle):

```bash
npm run cycle -- --user illia.herasymets@gmail.com --source linkedin \
  --query "node.js" --location Remote \
  --include "node,typescript,javascript,full stack,fullstack,backend,frontend,software engineer" \
  --exclude "java,android,ios,c++,qa,data engineer,machine learning,devops,sap,abap"
```

Повторный сбор безопасен: вакансии, которые уже есть в базе (по URL), не пишутся второй раз, а
повторы с тем же названием и компанией не оцениваются заново (строки `=`).

### Разовый прогон — основной способ сейчас

Сначала пробный (`--dry-run` ничего не пишет, только печатает):

```bash
npm run collect -- --user illia.herasymets@gmail.com --source linkedin \
  --query "node.js" --location Remote \
  --include "node,typescript,javascript,full stack,fullstack,backend,frontend,software engineer" \
  --exclude "java,android,ios,c++,qa,data engineer,machine learning,devops,sap,abap" \
  --dry-run
```

Вывод:

```
linkedin «node.js» стр. 1: карточек 25, новых 25, отсеяно по названию 14
  − Senior DevOps Engineer (название: исключено «devops») https://www.linkedin.com/jobs/view/…/
  + Lead Fullstack Engineer (Typescript/Node.js) with German — Blexity https://www.linkedin.com/jobs/view/…/
…
linkedin «node.js» (Remote)
  страниц 4, карточек 100, новых 100, из них отсеяно по названию 57; не записано (--dry-run), некорректных 0
  остановка: достигнут предел страниц источника
```

`+` — пойдёт дальше (сохранится как `found`), `−` — отсеяна по названию (сохранится как `rejected`).
Если список устраивает — та же команда **без `--dry-run`** запишет всё в базу.

Параметры:

| Флаг | Что делает |
|---|---|
| `--query` | что искать на LinkedIn (ищет широко: в выдаче будут и нерелевантные) |
| `--location` | `Remote` — только удалённые; иначе город или страна (`"Dublin, Ireland"`) |
| `--include` | через запятую; в названии должно быть хотя бы одно слово. Пусто — любое |
| `--exclude` | через запятую; любое слово отсеивает. Сильнее `--include` |
| `--dry-run` | только печать, без записи |
| `--max-minutes` | предел времени (по умолчанию 60). Ctrl+C тоже останавливает, дописав страницу |

Слова фильтра ищутся целиком и без учёта регистра: `java` отсеет «Java Developer», но не
«JavaScript Developer»; `node` найдёт «Node.js»; `c++` и `.net` пишутся как есть.
Фильтр грубый: «Embedded Software Engineer» пройдёт через `software engineer`. Точный отбор — этап 2.

### Сохранённые поиски — для расписания

Поиск можно сохранить в базе, тогда `npm run collect` без аргументов прогонит все включённые
поиски и запишет отчёт каждого в `search_runs`. Пока поиски заводятся через API:

1. `npm run dev` — поднимает API на `:3400`.
2. Открой `http://localhost:3400/docs` (Swagger; с другой машины — через SSH-туннель).
3. `POST /api/auth/login` с `{ "email": "…", "password": "…" }` — cookie сессии поставится сам.
4. `POST /api/searches`:
   ```json
   { "source": "linkedin", "keywords": "node.js", "location": "Remote",
     "includeTitle": ["node", "typescript", "backend"], "excludeTitle": ["java", "qa"] }
   ```
5. Дальше: `npm run collect` (все поиски) или `npm run collect -- --user <email>` (только твои).

Там же: `GET /api/searches` — список, `PATCH /api/searches/{id}` — изменить или выключить
(`{"enabled": false}`), `GET /api/searches/{id}/runs` — история прогонов.

### Оценка найденных — `npm run score`

После сбора у тебя вакансии в `found`. Оценка проходит по ним всем (старые первыми), ставит
`queued` / `rejected` / `skipped` и в конце отправляет `queued` в Job-Tracker. Сначала пробно:

```bash
npm run score -- --user illia.herasymets@gmail.com --limit 10 --dry-run
```

Вывод (фрагмент живого прогона 2026-11-03 с `--no-push`: 10 вакансий, причины сокращены; строки `=`, `~` и `!`
в нём не встретились, их формат — ниже):

```
illia.herasymets@gmail.com
  − 45 Senior Full Stack Product Engineer (TypeScript) — Maze: Эта вакансия требует уровня Senior с опытом более 8 лет…
  + 75 Backend Software Engineer - AI Finance Agent — BJAK: Кандидат имеет необходимый опыт и навыки для роли бэкенд-инженера в финтехе…
  − 25 Staff Backend Engineer (all genders) – Remote within the EU — F11: Эта вакансия требует уровня Staff Engineer…
  …
  модель qwen3.5:4b, профиль rev 1, порог 50
  queued 1, rejected 9, skipped 0, ошибок 0; ~16.6 с на вакансию, токены 43453/2540
  Job-Tracker: не отправлялось (--no-push)
```

Остальные виды строк:

```
  = повтор <название> — <компания> ← <название> — <компания> (<id двойника>)
  ~ статус сменился <название> — <компания>: оставлена как есть
  ! ошибка <название> — <компания>: Ollama: ответ не разобран после повтора (…)
```

С `--dry-run` последняя строка — `не записано (--dry-run), в Job-Tracker не отправлено`.

`+` в очередь (оценка ≥ порога), `−` отклонена (причина — текст после двоеточия, он же `why`),
`=` повтор уже оценённой вакансии (модель не спрашивается), `~` статус сменился во время оценки,
`!` ошибка ответа модели — вакансия остаётся `found` и будет оценена в следующий раз.

Без `--dry-run` всё пишется в базу, и последняя строка становится отчётом Job-Tracker:

```
  Job-Tracker: отправлено 1, повторы 0, уже подавался 0, дослано оценок 0, осталось 0
```

| Флаг | Что делает |
|---|---|
| `--user` | только этот пользователь; без него — все активные (не привязанные к JT пропускаются) |
| `--limit N` | не больше N вакансий на пользователя |
| `--dry-run` | только печать: ничего не пишет и не отправляет в JT |
| `--model NAME` | другая модель Ollama на этот прогон (удобно сравнивать модели с `--dry-run`) |
| `--threshold N` | порог для `queued`, по умолчанию 50 |
| `--no-push` | оценить, но не отправлять в JT (отправить потом: `POST /api/tracker/push` или следующий `npm run score`) |

Ctrl+C дописывает текущую вакансию и останавливает прогон; отправка в JT после Ctrl+C не делается.
Пользователь, не привязанный к JT, печатается как «пропущен» (с `--user` — код выхода 1).
За один прогон в JT уходит не больше 50 вакансий (лимит JT — 60 запросов в минуту), остаток —
`осталось N` — уйдёт следующим прогоном. Как устроена оценка и почему так — [overview.md](overview.md#42-отбор-).

### Какую модель брать — сравнение на живых данных

Модели сравниваются на одних и тех же вакансиях: `npm run score -- --user … --dry-run --model <модель>`
(ничего не пишется). Прогон 2026-11-03 на копии базы: 17 вакансий LinkedIn, профиль JT rev 1, GTX 1060.

| Модель | Скорость | Итог |
|---|---|---|
| `qwen3.5:4b` | ~14 с на вакансию (первая, с загрузкой модели, — ~45 с) | JSON валиден в 100% ответов. При пороге 50 в `queued` 4 из 17: BJAK ×3 (85, 85, 75) и Tether AgenticOps (75). Остальные — Senior 5+ и Staff — получили 15–45 и ушли в `rejected` с понятными причинами («требует 5+ лет…», «нужна степень…», «работа из Германии без права работы в ЕС») |
| `qwen3:4b-instruct-2507-q4_K_M` | ~18 с на вакансию | оценивает ниже: 0 из 17 набрали ≥ 70 |

Поэтому по умолчанию стоит `qwen3.5:4b`. Порог снижен с 70 до 50 по твоему решению: на этих 17 вакансиях
ты подался бы на всё, кроме совсем неподходящих, а модель строга к Senior-вакансиям. Если отбор окажется
слишком строгим или мягким, порог можно подобрать флагом `--threshold` в `--dry-run`, не меняя код.
Учти: `queued` с оценкой 50–69 приходят в Job-Tracker как `WEAK_FIT` ([trackers.md](trackers.md#отправка-вакансий)).

### Сбор, оценка и отправка одной командой — `npm run cycle`

Один прогон конвейера: сохранённые поиски (или разовый поиск) → оценка всех `found`, включая
оставшиеся с прошлых прогонов → отправка `queued` в Job-Tracker. Это то, что потом будет запускать
таймер. Пробно:

```bash
npm run cycle -- --user illia.herasymets@gmail.com --dry-run
npm run cycle -- --user illia.herasymets@gmail.com --source linkedin --query "node.js" --location Remote \
  --exclude "java,android,qa" --dry-run      # разовый поиск вместо сохранённых
npm run cycle -- --user illia.herasymets@gmail.com --skip-collect   # только оценка и отправка
```

| Флаг | Что делает |
|---|---|
| `--user` | только этот пользователь (сбор и отбор); без него — все активные |
| `--source`, `--query`, `--location`, `--include`, `--exclude` | разовый поиск, как в `npm run collect`; нужны `--user`, `--source` и `--query`; с `--skip-collect` не сочетаются |
| `--skip-collect` | без сбора: только оценка уже найденных и отправка |
| `--dry-run` | сбор и оценка без записи; в JT ничего не уходит |
| `--no-push` | оценить, но не отправлять в JT |
| `--max-minutes N` | общий предел на весь прогон (по умолчанию 60): что не потратил сбор, достаётся отбору; если время кончилось во время сбора, отбор не запускается |
| `--model`, `--threshold` (0–100, по умолчанию 50), `--limit` (1–10000, самые старые `found`) | как в `npm run score` |

Вывод идёт секциями `== Сбор ==` и `== Отбор ==` (строки те же, что у `collect` и `score`),
в конце — итог тремя строками (формат из `scripts/pipeline-cli.ts`, числа условные):

```
Итог цикла:
  сбор: поисков 1, новых 51, отсеяно по названию 29, записано 51; остановка: достигнут предел страниц источника ×1
  отбор: queued 6, rejected 14, skipped 2, ошибок 0
  Job-Tracker: отправлено 6, повторы 0, уже подавался 0, дослано оценок 0, отклонено JT 0, осталось 0
```

Что бывает при сбоях:

| Ситуация | Что делает `cycle` |
|---|---|
| брокер браузера не отвечает | сбор пропущен, отбор идёт по уже найденным |
| ошибка источника (например, вход в LinkedIn) | код выхода 1, но отбор всё равно идёт |
| Ollama недоступна или модель не скачана | отбор останавливается, код выхода 1 |
| JT не настроен (`JOB_TRACKER_*` пусты) | отбор пропущен, код выхода 1 |
| пользователь не привязан к JT | он пропущен (с `--user` — код выхода 1) |
| Ctrl+C или истёк `--max-minutes` во время отбора | текущая вакансия дописывается, в JT не отправляется |

### Где смотреть результат

Веб-страницы вакансий пока нет. Варианты:

- **Вывод самих команд.** `collect`, `score` и `cycle` печатают каждую вакансию строкой
  `+`/`−` с оценкой и причиной — это первый и самый быстрый взгляд.
- **Терминал, прямо из базы** (только чтение, сервер запускать не нужно). Из корня проекта;
  последний аргумент — статус (`queued`, `rejected`, `found`, …):

  ```bash
  cd server && node -e '
  const db = require("better-sqlite3")("data/job-autopilot.db", { readonly: true });
  console.table(db.prepare("select status, count(*) n from jobs group by status").all());
  for (const j of db.prepare("select score, title, company, why, url from jobs where status = ? order by score desc").all(process.argv[1]))
    console.log(`${j.score}  ${j.title} — ${j.company}\n     ${j.why}\n     ${j.url}`);
  ' queued; cd ..
  ```

  Сначала таблица «сколько в каком статусе», потом вакансии этого статуса от лучшей оценки к худшей.
  У отсеянных фильтром по названию оценки нет (`null`), причина — `название: исключено «…»`
  или `название: нет ни одного из …`.
- **Swagger** (`npm run dev`, `http://localhost:3400/docs`, после входа):
  `GET /api/jobs?status=queued&sort=score` — отобранные от лучшей оценки, `GET /api/jobs?status=found` — найденные, `GET /api/jobs?status=rejected` — отсеянные с причиной
  в `why`, `GET /api/jobs/{id}` — с описанием, `GET /api/jobs/summary` — счётчики по статусам.
- Вернуть отсеянную в работу: `PATCH /api/jobs/{id}` с `{"status": "queued"}`. Она уйдёт в JT
  при следующем `npm run score` (или `POST /api/tracker/push`), но без оценки, если модель её не оценивала.
- **Job-Tracker**, список To Apply: отобранные вакансии с оценкой, verdict и причиной.
  Состояние связи — `GET /api/tracker/status`, профиль, по которому оценивали, — `GET /api/tracker/profile`.

## 5. Если что-то не так

| Симптом | Причина и что делать |
|---|---|
| `DATABASE_URL не задан` | нет `.env`: `npm run setup` в корне |
| `Активный пользователь … не найден` | `npm run user:create -- --email … --name …`; проверь email (одна `@`) |
| `BrowserUnavailableError: browser broker is not running` | не запущен agent Chromium/брокер: `systemctl status agent-browser-broker agent-chromium` |
| `LinkedIn требует вход или проверку (/login …)` | сессия LinkedIn истекла или капча: войди через noVNC, повтори |
| `BrowserBlockedError: blocked by browser policy` | URL не в allow-list брокера (сейчас разрешены только `linkedin.com` и `example.com`) |
| `page changed while reading …` | вкладку увёл кто-то другой (Telegram-бот, local-agent) — не пользуйся ими во время сбора |
| `карточек 7` вместо 25 на странице | LinkedIn не догрузил выдачу за 8 шагов прокрутки; недобранное попадёт в следующий прогон |
| `LinkedIn открыл AI-поиск (/jobs/search-results) вместо обычной выдачи` | LinkedIn проигнорировал `skipRedirect=true` и увёл аккаунт на новый AI-поиск, где нет ссылок на вакансии. Поиски LinkedIn в этом прогоне остановлены. Открой выдачу в agent Chromium через noVNC и проверь, что это `/jobs/search/`; если LinkedIn поменял поведение, нужна правка `LinkedinParser.ts` (`searchUrl`) |
| в описании мусор или пустая компания | LinkedIn поменял вёрстку или интерфейс не английский — сохрани страницу как фикстуру и поправь `LinkedinParser.ts` |
| `Job-Tracker не настроен: задайте JOB_TRACKER_URL и JOB_TRACKER_TOKEN` | `npm run score` без JT не работает: профиль берётся оттуда. Заполни обе переменные в `.env` |
| `пропущен: не привязан к Job-Tracker` | email пользователя autopilot не совпадает с владельцем токена JT. Проверь email или создай токен под нужным пользователем JT |
| `пропущен: Job-Tracker отклонил токен (HTTP 401/403)` | токен неверный, отозван или без нужного scope — создай новый со всеми четырьмя scopes |
| `остановлен: модель недоступна — Ollama … недоступна: …ECONNREFUSED` | Ollama не запущена: `systemctl status ollama` или `ollama serve`; проверь `OLLAMA_URL` |
| `остановлен: модель недоступна — Ollama HTTP 404: model "…" not found` | модель не скачана: `ollama pull <модель>` или поправь `OLLAMA_MODEL` / `--model` |
| `…нет ответа за 120000 мс` | модель не успевает (холодный старт, слабая GPU): повтори или увеличь `OLLAMA_TIMEOUT_MS` |
| `! ошибка …: промпт занял N токенов при пределе …` | профиль + описание не влезли в контекст: увеличь `OLLAMA_NUM_CTX` или сократи профиль в JT |
| `профиль rev N (из кеша: Job-Tracker недоступен)` | JT не ответил или вернул 429 — оценка идёт по сохранённой копии профиля; это не ошибка |
| `Job-Tracker: ошибка — Job-Tracker: превышен лимит запросов…` (429) | лимит JT 60 запросов в минуту; созданное не потеряется, остаток и оценки дошлются следующим прогоном через минуту |
| `Job-Tracker: … осталось N` | в одну пачку уходит до 50 вакансий; запусти `npm run score` ещё раз |

Важно: вкладка agent Chromium **одна** и общая с Telegram-ботом и local-agent. Пока идёт сбор,
не давай им задания с браузером.
