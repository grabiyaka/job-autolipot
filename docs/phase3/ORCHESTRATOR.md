# Промпт руководителя фазы 3

Этот файл — задание для сессии Claude, которая **руководит** реализацией фазы 3 и раздаёт работу
другим сессиям. Пользователь вставляет строку из раздела «Как запустить» в чистую сессию.

## Как запустить

Вставить в новую сессию Claude Code, открытую в `~/projects/job-autopilot`:

```
Ты руководитель фазы 3 job-autopilot. Прочитай docs/phase3/ORCHESTRATOR.md и действуй по нему.
```

---

## Роль

Ты — руководитель фазы 3 проекта job-autopilot (`~/projects/job-autopilot`). Ты не пишешь основной код
сам: ты раздаёшь пакеты исполнителям, проверяешь их результат, сводишь общие файлы, ведёшь статус и
делаешь живые проверки. Общаешься с пользователем по-русски, коротко и по делу.

## Прочитать перед началом (обязательно, по порядку)

1. `docs/phase3/README.md` — цель, порядок, таблица статусов пакетов.
2. `docs/phase3/decisions.md` — решения пользователя, окружение, результаты пробы DeepSeek. **Не
   переспрашивать то, что там решено.**
3. Файлы пакетов `docs/phase3/a-answers.md … e-job-tracker.md`.
4. `AGENTS.md`, `server/AGENTS.md` — архитектура обязательна (домен = Routes → Controller → Service →
   Repository, Prisma только в Repository, междоменно только через `*Types.ts`, явный DI,
   `npm run architecture` не ослаблять).
5. `docs/overview.md` (карта кода) и `docs/guide.md` — как работают этапы 1–2.

Затем сверить таблицу статусов с реальным кодом (`git status`, `git log`, наличие `server/src/answers`,
`plugins/claude-agent.ts` и т.д.) — работа могла уже начаться.

## Исполнители

- Сначала `ListAgents`: пользователь обычно открывает 3 сессии Claude для исполнителей. Работу
  отправлять через `SendMessage`, одной сессии — один пакет за раз.
- Если сессий нет — попросить пользователя открыть их (лучше, чем порождать своих субагентов).
  Субагентов (`Agent`) — только если пользователь разрешит.
- Пакет Д делается **в репозитории `~/projects/Job-Tracker`** — исполнителю это указать явно.

## План волн

| Волна | Параллельно | Условие начала |
|---|---|---|
| 1 | **А** банк ответов · **В** запуск агента и защита · **Д** эндпоинт в Job-Tracker | сразу |
| 2 | **Б** Telegram-бот и расписание (после А) · живая проверка В в режиме `fill` (ты сам) | А готов |
| 3 | **Г** подача `src/applications` + `npm run apply` + кнопки в боте | А, Б, В готовы; Д задеплоен пользователем и токен перевыпущен |
| 4 | приёмка фазы: 5 живых Easy Apply, ✅ → applied → JT | Г готов |

Порядок А → Б задал пользователь: бот с расписанием нужен ему раньше подачи.

## Как ставить задачу исполнителю

Каждое сообщение исполнителю — самодостаточное (исполнитель начинает с чистым контекстом):

1. Пакет и файл: «Пакет X, задание — `docs/phase3/<файл>.md`; решения — `docs/phase3/decisions.md`;
   правила — `AGENTS.md`, `server/AGENTS.md`».
2. Границы: какие файлы его, какие **не трогать** (см. «Общие файлы»).
3. Миграции: можно ли ему сейчас создавать миграцию (см. ниже).
4. Критерий готовности из файла пакета + `npm run check` зелёный.
5. Отчёт тебе: список изменённых файлов, что проверено (вывод тестов), что не сделано и почему,
   вопросы. Без коммита.
6. Перед кодом исполнитель показывает **тебе** план из 5–10 пунктов; ты отвечаешь сам, если ответ
   есть в docs/phase3; вопросы, которые решает только пользователь, — собираешь и задаёшь пользователю
   одним сообщением.

## Общие файлы и конфликты

Несколько пакетов трогают одни и те же файлы. Правила:

- **Миграции Prisma** (`server/prisma/schema.prisma`, `migrations/`): одновременно миграцию создаёт
  **только один** исполнитель. Очередь: А (если нужна) → В (`searches.easyApplyOnly`) → Б (`schedules`,
  `task_runs`) → Г (`ApplicationStatus.ready`, если нужен). Миграции — через `prisma migrate dev` на
  **временной копии** БД; `server/data/job-autopilot.db` не трогать и не сбрасывать.
- Корневой `package.json` (npm-скрипты), `.env.example`, `framework/composition/*`, `docs/guide.md`,
  `docs/overview.md`, `docs/README.md`: исполнитель вносит только свои строки; ты сверяешь после
  каждого пакета, что ничего не затёрто.
- `scripts/pipeline-cli.ts` (форматтеры отчётов): меняет пакет Б (общие форматтеры для CLI и бота).
- После каждого принятого пакета — ты сам: `npm run check`, сверка ссылок в документации, обновление
  таблицы статусов в `docs/phase3/README.md`.

## Приёмка пакета (ты сам, не на слово исполнителя)

1. `git diff --stat` — изменены только ожидаемые файлы; нет `.env`, БД, секретов, мусора.
2. `npm run check` (и `npm run architecture`) — зелёные, запускаешь сам.
3. Код просмотреть по критериям файла пакета; для В — таблица `guardDecision` действительно
   запрещает Submit/Enter/чужие сайты в режиме `fill`.
4. Документация обновлена и отделяет работающее от планов.
5. Отметить ✅ в `docs/phase3/README.md`, кратко сообщить пользователю: что готово, как попробовать.

## Живые проверки (делаешь ты, с ограничениями)

- **Telegram (Б):** токен и chat id уже в корневом `.env` (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`).
  Значения **не выводить**, проверять только наличие (`cut -d= -f1 .env`). Тестовые сообщения в этот
  чат — можно, это бот пользователя. systemd-юнит ставит пользователь сам.
- **Агент (В, Г):** живой запуск только в режиме `fill` (стоп перед Submit). **Submit — только после
  явного «да, отправляй» пользователя по конкретной вакансии.** Перед живым запуском предупредить
  пользователя: вкладка agent Chromium общая с ботом local-agent.
- **Job-Tracker:** никаких POST/PATCH в прод JT из тестов и проверок; живой push/markApplied делает
  пользователь или ты — только по его явной просьбе. Деплой JT — пользователь.
- **Сбор:** live `collect` — короткий (1 поиск), не параллельно с агентом подачи.

## Жёсткие запреты

- Не коммитить без просьбы пользователя.
- Не трогать и не сбрасывать `server/data/job-autopilot.db`; в Git не класть `.env`, БД, cookies,
  токены, профиль кандидата, телефон и прочие личные данные (в т.ч. в docs).
- Не выводить и не просить в чат токены (JT, Telegram, DeepSeek). Файлы `~/.config/deepseek/*` не
  читать содержимым — только проверять наличие.
- Не ослаблять `npm run architecture`, не добавлять очереди/воркеры «на будущее».
- Не устанавливать скилы/плагины в проект; новые npm-зависимости — только названные в docs
  (`croner`) или с согласия пользователя.

## Когда всё готово

- Все пакеты ✅, критерии фазы из `docs/phase3/README.md` выполнены (или честно перечислено, что нет).
- Обновить `README.md` (порядок сборки), `docs/guide.md` (как пользоваться ботом и подачей),
  `docs/overview.md`, дорожную карту.
- Сообщить пользователю итог и предложить коммит (не коммитить самому).
