# Пакет Б. Telegram-бот и расписание

Бот — пульт управления конвейером: запустить сбор или оценку сейчас, настроить расписание (cron),
включить и выключить его, получить отчёт. Позже (пакет Г) туда же добавляются подача, вопросы
агента и кнопка ✅ «отправить».

## Почему отдельный бот

- Работающий `agent-tg-bot.service` — универсальный Python-агент local-agent (Ollama + MCP), чужой
  код и деплой (`home-server-infra`). Встраивать туда конвейер — смешать два проекта.
- Новый бот живёт в job-autopilot, на том же Node/TS, и вызывает сервисы напрямую, а не через CLI.
- Нужно от пользователя: новый бот у @BotFather → `TELEGRAM_BOT_TOKEN`, и свой chat id →
  `TELEGRAM_CHAT_ID` (бот отвечает только этому чату, остальным — молчит).

## Как устроено

Один долгоживущий процесс `npm run bot` (`server/scripts/bot.ts`), под systemd.

```
bot.ts
 ├─ plugins/telegram.ts        getUpdates (long polling) / sendMessage / editMessage / answerCallbackQuery
 ├─ src/schedules              расписание в базе + планировщик (следующий запуск, вкл/выкл)
 └─ запуск задач в процессе    те же сервисы, что у CLI: collect / score / cycle (позже apply)
```

- **Telegram-клиент** — `plugins/telegram.ts` на `fetch` к Bot API, без библиотеки (нужны 4 метода).
  Ретраи на 429 по `retry_after`. Тесты — на фейковом HTTP, как `job-tracker.test.ts`.
- **Задачи выполняются в процессе бота**, через composition (`create-collector`, `create-scorer`),
  а не дочерним `npm run …`: так в Telegram приходит структурированный отчёт, а не текст консоли,
  и `/stop` работает через `AbortController`, как Ctrl+C в CLI.
- **Одна задача за раз.** Пока идёт задача, новые запуски (ручные и по расписанию) отвечают
  «занято: <что идёт>, запущено N мин назад». Плюс файловый lock браузера из пакета В, общий с CLI:
  если ты запустил `npm run collect` в терминале, бот это увидит.
- **Отчёт** после задачи — те же итоговые строки, что печатает CLI (форматтеры в `scripts/pipeline-cli.ts`
  вынести так, чтобы их использовали и CLI, и бот), плюс топ `queued` со ссылками.

## Расписание — домен `src/schedules`

Таблица `schedules` (миграция через `prisma migrate dev` на копии БД):

| Поле | Значение |
|---|---|
| `id`, `userId` | владелец |
| `task` | `collect` \| `score` \| `cycle` (позже `apply`) |
| `cron` | выражение cron, например `0 9,18 * * *` |
| `timezone` | по умолчанию `Europe/Dublin` |
| `enabled` | вкл/выкл |
| `options` | JSON флагов задачи (`limit`, `threshold`, `maxMinutes`…) |
| `lastRunAt`, `lastStatus`, `lastSummary` | итог последнего запуска |

- Разбор cron — библиотека `croner` (маленькая, без зависимостей): `nextRun()` с часовым поясом.
  Свой парсер не писать.
- Планировщик: при старте и после каждого изменения считает ближайший запуск, ставит один `setTimeout`.
  Пропущенные запуски (бот был выключен) **не догоняются** — следующий по расписанию.
- История ручных и плановых запусков: таблица `task_runs` (`task`, `trigger: manual|schedule`,
  `startedAt`, `finishedAt`, `status`, `summary`) — `/status` показывает последние.
- Сохранённые поиски (`searches`) остаются как есть: `collect` и `cycle` в боте гоняют включённые поиски.

## Команды бота

| Команда | Что делает |
|---|---|
| `/status` | счётчики вакансий по статусам, что выполняется сейчас, последние 5 запусков, ближайшие по расписанию |
| `/run collect` · `/run score` · `/run cycle` | запустить сейчас; в конце — отчёт |
| `/stop` | остановить текущую задачу (дописать текущую вакансию/страницу) |
| `/schedule` | список расписаний с кнопками вкл/выкл и «удалить» |
| `/schedule cycle 0 9,18 * * *` | создать или заменить расписание задачи |
| `/on cycle` · `/off cycle` | включить / выключить расписание задачи |
| `/searches` | сохранённые поиски с кнопками вкл/выкл |
| `/queued` | лучшие 10 отобранных: оценка, название, компания, ссылка |
| `/answers` | банк ответов (пакет А); `/answer <вопрос> = <ответ>` — добавить |

Позже, с пакетом Г: `/run apply`, сообщения «готово к отправке» с кнопками ✅ / ❌, вопросы агента
(ответ реплаем → банк ответов → `--resume`), расписание для `apply`.

## Деплой

- `deploy/job-autopilot-bot.service` (пример юнита в репозитории; ставит пользователь сам):
  `User=elijah`, `WorkingDirectory=…/job-autopilot`, `ExecStart=npm run bot`, `Restart=on-failure`.
- Переменные в корневом `.env`: `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`; в `.env.example` — пустые.

## Конфликт за браузер

agent Chromium один на всех: сборщик (брокер), подача (Playwright MCP) и бот local-agent.
Lock из пакета В защищает только job-autopilot. Боту local-agent можно отдельно добавить проверку
того же lock-файла — это правка в local-agent, делается по просьбе пользователя. До тех пор:
не давать боту local-agent задач с браузером во время прогонов по расписанию.

## Тесты

- `plugins/telegram.ts`: фейковый Bot API (getUpdates, 429 с `retry_after`).
- Расписание: `nextRun` в `Europe/Dublin` (включая переход на зимнее время), вкл/выкл, «занято».
- Бот: разбор команд, чужой chat id игнорируется, `/run` → фейковые сервисы → отчёт.

## Готово, когда

- `/run cycle` из Telegram прогоняет сбор и оценку и присылает итог;
- `/schedule cycle 0 9,18 * * *` + `/on cycle` запускают цикл в 9:00 и 18:00, `/off cycle` выключает;
- `npm run check` зелёный, документация: `docs/telegram.md`, guide.md, overview.md.
