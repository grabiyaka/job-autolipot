# Telegram-бот и расписание

Бот — пульт конвейера. Он запускает сбор и оценку сейчас, держит расписание (cron), включает и
выключает его и присылает отчёт. Это отдельный бот job-autopilot: универсальный бот local-agent
(`agent-tg-bot.service`) он не заменяет и не трогает. Как пользоваться — в
[guide.md](guide.md#telegram-бот-и-расписание--npm-run-bot). Постановка задачи — в
[phase3/b-telegram.md](phase3/b-telegram.md).

Обозначения: ✅ работает в коде, 📝 план.

## Запуск ✅

1. В корневом `.env` должны быть заданы `TELEGRAM_BOT_TOKEN` (бот от @BotFather) и `TELEGRAM_CHAT_ID`
   (твой chat id). Остальные настройки — в таблице ниже.
2. База должна быть на последней миграции `20261104123152_schedules_task_runs` (таблицы `schedules`
   и `task_runs`): `npm run db:migrate`.
3. `npm run bot` — один долгоживущий процесс с long polling. В журнале появится строка
   «Бот запущен для <email>; чат …; ближайший запуск по расписанию: …».

Под systemd используй пример [deploy/job-autopilot-bot.service](../deploy/job-autopilot-bot.service):
`User=elijah`, `WorkingDirectory` проекта, `ExecStart=/usr/bin/env npm run bot`, `Restart=on-failure`.
Юнит ставится вручную, команды есть в комментарии файла. Путь к Node из nvm прописан в `PATH` юнита.

На home-server бот работает **без sudo, как пользовательский юнит** (с 2026-11-08): копия юнита без `User=`, с
`WantedBy=default.target`, лежит в `~/.config/systemd/user/job-autopilot-bot.service`. Чтобы он стартовал при загрузке
без входа в систему, включён `loginctl enable-linger elijah`.

```
systemctl --user restart job-autopilot-bot    # после правок кода бота
systemctl --user status job-autopilot-bot
journalctl --user -u job-autopilot-bot -f
```

SIGTERM или Ctrl+C останавливает таймер расписания и текущую задачу: она дописывает страницу или
вакансию. Затем бот выходит. Если процесс убит посреди задачи, при следующем старте её запись в
`task_runs` закрывается как ошибка «прервано».

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | — | без них бот не стартует |
| `BOT_USER` | пусто | email владельца, от имени которого работает бот; пусто — единственный активный пользователь; если активных несколько — ошибка при старте |
| `SCHEDULE_TIMEZONE` | `Europe/Dublin` | часовой пояс новых расписаний |
| `BOT_SCHEDULED_REPORT` | `changes` | `changes` — отчёт о плановом запуске только при новых `queued` или ошибках; `always` — после каждого |
| `REMOTE_BROWSER_PUBLIC_URL` | пусто | публичный адрес [удалённого браузера](#удалённый-браузер-) (например `https://home-server.tail0147a9.ts.net:8444`); пусто — «🖥 Открыть браузер» отвечает «не настроен» |
| `REMOTE_BROWSER_PORT` | `3420` | локальный порт страницы браузера; слушает только `127.0.0.1` |

Бот использует те же настройки, что и CLI: `DATABASE_URL`, `AGENT_BROWSER_SOCKET`, `OLLAMA_*`,
`JOB_TRACKER_*`.

## Кто может командовать ✅

Бот отвечает только на сообщения и кнопки из чата `TELEGRAM_CHAT_ID`. Сообщения из других чатов
пропускаются молча, без ответа об ошибке. Команды старше 10 минут (отправленные, пока бот был выключен)
тоже пропускаются, поэтому перезапуск не повторяет старый `/run`.

Все действия выполняются от имени одного владельца: его вакансии, поиски, банк ответов и расписания.
Задачи бота работают только с этим владельцем. Для сравнения, CLI без `--user` обходит всех активных.

## Команды ✅

| Команда | Что делает |
|---|---|
| `/status` | вакансии по статусам (включая `manual` — подать вручную), что выполняется сейчас и на каком этапе (сбор — последняя страница поиска; оценка — сколько оценено, сколько в queued и последняя вакансия; подача — только этап; отправка после ✅ — «submit: <вакансия> — <компания>», у внешней формы с пометкой «заполняю заново и отправляю»), последние 5 запусков, ближайшие по расписанию |
| `/run collect` · `/run score` · `/run cycle` | запустить сейчас; бот сразу отвечает «Запускаю…», в конце присылает отчёт |
| `/run hunt` (`/hunt`) | другие биржи через агента Claude ([hunt.md](hunt.md)): поиски `@сайт` → выдача → описания новых → оценка → JT. В `/status` этап «сбор через агента» с последней строкой агента. Отчёт — строка на поиск: «indeed «node.js»: карточек 20, новых 8, с описанием 8, отсеяно по названию 3, 3 мин, $0.40; записано 11», при блокировке «indeed: нужна капча/вход — пропущено», затем итог агента (затраты за сегодня из `HUNT_MAX_USD_PER_DAY`), отбор и JT |
| `/run apply` | заполнить формы из JT To Apply (LinkedIn Easy Apply и внешние сайты), стоп перед отправкой; после отчёта — сообщение на каждую готовую форму с ✅ / ❌, на каждую вакансию «подать вручную» с «✅ подал сам» / «❌ не подаю» и на каждый вопрос агента ([подача](#подача-)) |
| `/pending` | заново прислать формы, ждущие ✅, вакансии «подать вручную» (с кнопками) и открытые вопросы |
| `/stop` | остановить текущую задачу (дописать текущую страницу или вакансию) |
| `/schedule` | список расписаний с кнопками ⏸/▶️ и 🗑 |
| `/schedule cycle 0 9,18 * * *` | создать или заменить расписание задачи; новое создаётся **выключенным**, ответ подсказывает «включить: /on cycle» |
| `/on cycle` · `/off cycle` | включить или выключить расписание задачи |
| `/searches` | сохранённые поиски с кнопками вкл/выкл (то же поле `enabled`, что в `PATCH /api/searches/:id`) и 🗑 удалить (история прогонов поиска удаляется, вакансии остаются) |
| `/search node.js \| Remote \| +node,backend \| -java,qa` | добавить сохранённый поиск LinkedIn, сразу включённый. Обязательны только ключевые слова; дальше части через `\|` в любом порядке: `+слова` — хотя бы одно в названии, `-слова` — отсеять, `all` — не только Easy Apply (по умолчанию только Easy Apply), часть без знака — локация. `/search` без аргументов — подсказка |
| `/search @indeed node.js \| Ireland \| +node \| -java` | поиск через агента (`source: agent`, `site`): `@indeed`, `@djinni`, `@remoteok`, `@wellfound` или `@https://адрес-страницы-поиска` (в адресе можно `{q}` и `{l}`). Части — как у LinkedIn, Easy Apply не бывает. Собирает его `/hunt`, не `/cycle`; в `/searches` виден как `@indeed «node.js» (Ireland)` |
| `/queued` | 10 лучших отобранных: оценка, название, компания, ссылка |
| `/answers` | банк ответов |
| `/answer <вопрос> = <ответ>` | записать ответ (`origin: telegram`); тот же вопрос в другой формулировке заменяет прежний |
| `/cycle` · `/collect` · `/score` · `/hunt` · `/apply` [флаги] | короткая форма `/run <задача>` — чтобы запускать из меню «/» без набора |
| `/help`, `/start` | «С чего начать» (поиск → `/cycle` → `/search @indeed …` и `/hunt` → `/queued` → `/apply` → `/pending`) и все команды |

При старте бот вызывает `setMyCommands` (`menuCommands` в `bot-commands.ts`): команды появляются в меню «/»
у поля ввода. Ошибка этого вызова только пишется в лог — набранные вручную команды работают и без меню.

Флаги к `/run` и `/schedule` пишутся после задачи (у `/schedule` — после 5 полей cron) как `ключ=значение`:

| Флаг | Задачи | Значение |
|---|---|---|
| `limit=N` | score, cycle, apply, hunt | не больше N вакансий при оценке; для apply — запусков агента (по умолчанию `APPLY_MAX_PER_RUN`); для hunt — описаний новых вакансий на поиск (1–50, по умолчанию 10), оценка без предела |
| `threshold=N` | score, cycle, hunt | с какой оценки вакансия идёт в `queued` (0–100) |
| `max=M` | все | предел длительности прогона, минуты (по умолчанию 60) |
| `easy` | collect, cycle | только вакансии с LinkedIn Easy Apply, на этот прогон |
| `skip-collect` | cycle | без сбора: оценка уже найденных и отправка |

Флаг, который не подходит задаче, отвергается с объяснением. `dry-run` и `no-push` в боте нет: их
место — CLI. Расписание подачи: `/schedule apply 0 10 * * 1-5 limit=3`, затем `/on apply`; оно только
заполняет формы, отправка — всегда после ✅. Расписание сбора с других бирж: `/schedule hunt 0 8 * * * limit=5`, затем `/on hunt`.

## Подача ✅

- `/run apply` (или по расписанию) идёт как задача бота: одна за раз, lock браузера берёт сервис подачи
  (`apply`); если браузер занят — «занято: …». Отчёт: строка на вакансию (ready, needs_input, manual,
  skipped с причиной, failed), «Подать вручную: N — ссылки ниже», затраты за сутки и лимит.
- На каждую заполненную форму — сообщение с кнопками **✅ отправить** / **❌ отказаться** (данные кнопок
  `a:ok:<id>` / `a:no:<id>`):
  - Easy Apply — «📝 Заполнено, ждёт ✅», ссылка на вакансию и все поля, которые заполнил агент;
  - внешняя форма (`kind: external`: Greenhouse, Lever, сайт компании…) — «🌐 Внешняя форма заполнена,
    ждёт ✅», хост `applyUrl` ссылкой, сводка «поле: значение» (значение до 150 символов, сообщение до
    3500 символов, остальное — «…и ещё N полей»), итог агента и пометка
    «✅ — агент заполнит форму заново и отправит (пара минут)».
  - ✅ — отправка в фоне под тем же правилом «одна задача за раз» (занято — бот так и ответит на кнопку).
    Сообщение с формой сразу заменяется на «⏳ Отправляю заявку: …» (Easy Apply) или
    «⏳ Заполняю заново и отправляю: … Это пара минут» (внешняя форма: новый прогон агента
    `submit_fresh`, около $0.02, считается в дневной лимит). Пока идёт отправка, `/status` пишет
    «submit: <вакансия> — <компания>». Итог отдельным сообщением: отправлено и отмечено в JT, JT не
    ответил (отметка уйдёт следующим прогоном), не отправлено (новые вопросы, нужен аккаунт → `manual`) и т. п.
  - ❌ — попытка и вакансия `skipped`, причина «отклонено вручную».
- На каждую вакансию, которую агент подать не может (`manual`: Workday, iCIMS, аккаунт, вход, капча,
  ссылка не https), — сообщение «🖐 Подать вручную: <вакансия> — <компания>» с причиной, ссылкой на
  форму (`applyUrl`) и кнопками **✅ подал сам** / **❌ не подаю** (`a:me:<id>` / `a:no:<id>`):
  - «✅ подал сам» — попытка `submitted`, вакансия `applied`, отметка в JT с `channel: company_site_manual`;
    сообщение заменяется на «🖐 Подано вручную: …», итог отметки в JT — отдельным сообщением, как после ✅;
  - «❌ не подаю» — как ❌: попытка и вакансия `skipped`, «отклонено вручную».
  - Повторное нажатие на уже отмеченную вакансию — ответ на кнопку «отмечается только для попытки manual…».
  - **🖥 Открыть браузер** (`a:br:<id>`) — [удалённый браузер](#удалённый-браузер-): завести аккаунт или войти
    прямо в браузере агента, затем «✅ Аккаунт готов» — агент заполнит эту вакансию заново.
- С `APPLY_AUTO_SUBMIT=true` агент отправляет форму сам, кнопок ✅ нет. На каждую отправленную —
  «🚀 Отправлено агентом: <вакансия> — <компания>»: ссылка на форму, итог отметки в JT, «Вопросы и ответы»
  (все поля «поле: значение», сообщение до 3500 символов), итог агента; следом — альбом скриншотов формы
  (`sendMediaGroup` по 10, один — `sendPhoto`). Скриншотов нет — так и написано; не отправились — предупреждение.
- Каждый вопрос агента — отдельным сообщением со ссылкой на форму. **Ответ реплаем** на него записывается
  в банк ответов (`origin: telegram`). Когда закрыт последний вопрос попытки, бот **сразу** заполняет форму
  заново в фоне (`fillNext` с `jobId`, «одна задача за раз»): по черновику — полям прошлой попытки — и банку
  ответов; с `APPLY_AUTO_SUBMIT` — и отправляет. Итог — «apply после ответа» и сообщения как после `/run apply`.
  Если бот занят, вакансия остаётся `queued` до следующего `/run apply`. Реплай на другое сообщение — обычный
  текст («Не понял»).
- Плановый `apply` присылает отчёт, если есть готовые или отправленные формы, вопросы, вакансии «подать вручную»
  или проблемы.

Подробно о подаче — [applications.md](applications.md).

## Удалённый браузер ✅

Сайту нужен аккаунт (Workday, iCIMS, Taleo…) — агент ставит `manual`. Чтобы агент продолжил сам, аккаунт
заводится с телефона **в том же Chromium-профиле агента**: тогда сессия сайта уже есть, и агент работает дальше залогиненным.

- Агентский Chromium доступен только через Playwright MCP (`PLAYWRIGHT_MCP_URL`; он подключён к нему по CDP, вкладки
  и cookies общие с агентом). `plugins/remote-browser.ts` открывает в нём новую вкладку и управляет ею через
  `browser_run_code_unsafe`: эмуляция телефона по CDP (390 × высота экрана телефона, DPR 2, touch), снимок —
  `Page.captureScreenshot` (JPEG 60), тап, прокрутка колесом, ввод текста, Enter/⌫/Tab/Esc, назад, обновить.
  Все вызовы MCP идут одной очередью. Клиент MCP — `plugins/mcp-client.ts` (streamable HTTP на `fetch`, без SDK).
- `plugins/remote-browser-server.ts` — HTTP-сервер страницы на `127.0.0.1:REMOTE_BROWSER_PORT`, снаружи — через
  Tailscale HTTPS (`REMOTE_BROWSER_PUBLIC_URL`). Бот поднимает его на сессию и гасит после. Всё — под `/s/<token>`
  (24 случайных байта, base64url); другой путь, чужой или истёкший токен — 404. `GET /s/<token>` — одна страница без
  внешних скриптов (работает и как обычная страница, и как Telegram Mini App), `GET …/frame.jpg` — снимок (адрес страницы
  в `x-page-url`), `POST …/action` — JSON `tap {x,y}` (CSS px) · `scroll {dy}` · `text {text}` · `key {key}` · `back` ·
  `reload` · `goto {url}` · `resize {height}`.
- Страница: снимок во всю ширину (высота вьюпорта подстраивается под экран телефона), тап — клик, свайп и колесо —
  прокрутка, поле + «Отправить» — текст в поле, где стоит фокус, кнопки ⌫ ↵ Tab ← Назад ⟳ (перезагрузить). Новый кадр — после
  каждого действия и раз в 1,5 с.
- Настройка Tailscale (один раз): `sudo tailscale set --operator=$USER`, затем
  `tailscale serve --bg --https=8444 http://127.0.0.1:3420` (порты 443 и 8443 на home-server заняты), в `.env` —
  `REMOTE_BROWSER_PUBLIC_URL=https://home-server.tail0147a9.ts.net:8444`. Адрес открывается только в tailnet: на телефоне
  должен быть включён Tailscale. Пока сессии нет, адрес отвечает 502, так и должно быть. Выключить: `tailscale serve --https=8444 off`.
- Сессия одна. Закрывается через 30 мин без действий (опрос кадров действием не считается) и через 60 мин в любом случае.

Поток в боте:

1. «🖥 Открыть браузер» у сообщения «🖐 Подать вручную» (и в `/pending`). Бот занят — «занято: …». Иначе бот берёт
   слот «одна задача за раз» (`TaskRunner.hold`) и lock браузера (`bot:browser`) на всю сессию — ни задача, ни расписание,
   ни CLI браузер в это время не трогают, — открывает `applyUrl` попытки и присылает «🖥 Браузер открыт: <хост>…» с
   кнопками **🖥 Открыть** (`web_app`; не https-адрес — обычная ссылка), **✅ Аккаунт готов** (`a:acc:<id>`),
   **✖️ Закрыть** (`a:bx:<id>`). `/status` пишет «браузер (<хост>), запущено N мин назад».
2. «✅ Аккаунт готов» — сессия закрывается (эмуляция снята, вкладка закрыта, сервер остановлен, lock и слот отпущены),
   «Аккаунт готов — запускаю агента на эту вакансию…», и в фоне идёт `fillNext` с `jobId` и `accountReady`: агент
   начинает с формы `manual`-попытки ([applications.md](applications.md#правила-агента)). Дальше — обычный отчёт и ✅.
3. «✖️ Закрыть», `/stop`, остановка бота или таймаут — сессия закрывается, «Браузер закрыт.».

Текст, набранный на странице (в том числе пароль), уходит в Playwright MCP внутри кода `browser_run_code_unsafe`; бот
его не пишет в журнал.

## Задачи и отчёт ✅

Задачи выполняются в процессе бота через те же сервисы, что и CLI (`createCollector`, `createScorer`).
Общие прогоны находятся в `server/scripts/pipeline-tasks.ts` (`collectJobs`, `scoreOwners`, `runCycle`, `runHunt`),
форматтеры итогов — в `server/scripts/pipeline-cli.ts`. Поэтому `cycle` в боте ведёт себя как
`npm run cycle`:

- если брокер браузера недоступен или браузер занят, сбор пропускается, а отбор идёт;
- если Job-Tracker не настроен, отбор пропускается, и это ошибка;
- если Ollama недоступна, отбор останавливается.

`collect` и `cycle` гоняют включённые сохранённые поиски LinkedIn владельца, `hunt` — его поиски через агента
(`source: agent`), затем оценивает и отправляет так же, как `cycle` (`createHunter`, [hunt.md](hunt.md)).

Отчёт содержит те же итоговые строки, что печатает CLI («Итог цикла: …»), и длительность прогона.
Если появились новые `queued`, к отчёту добавляются 5 лучших `queued` со ссылками. Построчный вывод
(каждая вакансия, каждая страница) уходит в журнал процесса, а не в Telegram.

Когда приходит отчёт:

- после `/run` — всегда;
- после планового запуска — только если есть новые `queued` или проблемы: ошибка поиска, ошибки
  оценки, недоступная модель, ошибка отправки в JT, «занято». При `BOT_SCHEDULED_REPORT=always` — всегда.

## Одна задача за раз ✅

- Внутри бота одновременно идёт только одна задача. Новый запуск, ручной или плановый, получает
  ответ «занято: cycle, запущено N мин назад». Такой запуск попадает в историю со статусом `busy`.
- Для браузера бот берёт тот же файловый lock `server/data/browser.lock`, что и CLI
  ([agent-runner.md](agent-runner.md#блокировка-браузера-pluginsbrowser-lockts)):
  - `/run collect` берёт lock на весь прогон (`task: bot:collect`); если lock держит, например,
    `npm run collect` в терминале, ответ — «занято: браузер — collect (pid …), запущено N мин назад»;
  - `cycle` берёт lock только на сбор: если браузер занят, сбор пропускается с этой причиной, отбор идёт;
  - `/run hunt` берёт lock на весь прогон (`task: bot:hunt`), как `collect`: браузер занят — «занято: браузер — …», агент не запускается.
- `npm run collect` в терминале, пока бот собирает, падает с «браузер занят: bot:collect …».
- Бот local-agent об этом lock не знает. Пока идёт сбор по расписанию, не давай ему задач с браузером.

## Расписание — домен `schedules` ✅

- Таблица `schedules`: `userId`, `task` (`collect` | `score` | `cycle` | `apply` | `hunt`), `cron` (5 полей), `timezone`,
  `enabled`, `options` (JSON флагов), `lastRunAt`, `lastStatus`, `lastSummary`. На задачу одно
  расписание (`@@unique([userId, task])`). Новое создаётся выключенным, а при замене прежний `enabled`
  сохраняется.
- Таблица `task_runs`: `task`, `trigger` (`manual` | `schedule`), `scheduleId` (при удалении
  расписания становится `null`), `startedAt`, `finishedAt`, `status`, `summary` (текст отчёта, до 2000
  символов). Статусы: `running → ok | error | aborted`, а `busy` означает, что запуск не начался.
- Выражения cron разбирает библиотека `croner` (`plugins/cron.ts`, порт `CronCalendar` в
  `ScheduleTypes.ts`), с учётом часового пояса. В `Europe/Dublin` 9:00 остаётся 9:00 и после перехода
  на зимнее время: 08:00Z летом, 09:00Z зимой.
- Планировщик (`Scheduler` в `scripts/bot-runtime.ts`):
  - при старте, после каждого изменения расписаний и после каждого срабатывания считает ближайший
    запуск всех включённых расписаний и ставит один `setTimeout`;
  - таймер никогда не ждёт дольше часа, затем пересчитывает план: так замечается сдвиг часов;
  - перед запуском проверяет, что расписание не изменилось и не выключено;
  - пропущенные запуски не догоняются: если бот был выключен или машина спала дольше 5 минут после
    времени запуска, этот запуск пропускается, а в журнал пишется строка «пропущен запуск…»;
  - если два расписания совпали по времени, второе получит «занято».

HTTP API у расписаний нет: управление идёт только через бота.

## Клиент Bot API ✅

`server/plugins/telegram.ts` построен на `fetch`, без библиотеки. Методы: `getUpdates` (long polling
по 50 с), `sendMessage`, `editMessageText`, `answerCallbackQuery`, `sendPhotos` (файлы multipart:
`sendPhoto` или `sendMediaGroup` альбомами по 10, подпись — на первом снимке, до 1024 символов).

- На 429 клиент ждёт `parameters.retry_after` и повторяет запрос, до 3 раз. Если `retry_after` больше
  5 минут, клиент сдаётся.
- На 5xx и сетевые ошибки клиент повторяет запрос с растущей паузой, на остальные 4xx сразу выдаёт ошибку.
- Токен стоит в URL каждого запроса, поэтому в ошибках (`TelegramError`) нет ни URL, ни исходной
  ошибки fetch: только метод и описание от Telegram.
- Сообщения отправляются в HTML, весь текст из данных экранируется. Сообщение длиннее 4096 символов
  делится по строкам.
