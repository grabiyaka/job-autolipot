# Telegram-бот и расписание

Бот — пульт конвейера. Он запускает сбор и оценку сейчас, держит расписание (cron), включает и
выключает его и присылает отчёт. Это отдельный бот job-autopilot: универсальный бот local-agent
(`agent-tg-bot.service`) он не заменяет и не трогает. Как пользоваться — в
[guide.md](guide.md#telegram-бот-и-расписание--npm-run-bot). Постановка задачи — в
[phase3/b-telegram.md](phase3/b-telegram.md).

Обозначения: ✅ работает в коде, 📝 план.

## Запуск ✅

1. В корневом `.env` должны быть заданы `TELEGRAM_BOT_TOKEN` (бот от @BotFather) и `TELEGRAM_CHAT_ID`
   (твой chat id). Остальные настройки — в таблице ниже.
2. База должна быть на последней миграции `20261104123152_schedules_task_runs` (таблицы `schedules`
   и `task_runs`): `npm run db:migrate`.
3. `npm run bot` — один долгоживущий процесс с long polling. В журнале появится строка
   «Бот запущен для <email>; чат …; ближайший запуск по расписанию: …».

Под systemd используй пример [deploy/job-autopilot-bot.service](../deploy/job-autopilot-bot.service):
`User=elijah`, `WorkingDirectory` проекта, `ExecStart=/usr/bin/env npm run bot`, `Restart=on-failure`.
Юнит ставится вручную, команды есть в комментарии файла. Путь к Node из nvm прописан в `PATH` юнита.

SIGTERM или Ctrl+C останавливает таймер расписания и текущую задачу: она дописывает страницу или
вакансию. Затем бот выходит. Если процесс убит посреди задачи, при следующем старте её запись в
`task_runs` закрывается как ошибка «прервано».

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | — | без них бот не стартует |
| `BOT_USER` | пусто | email владельца, от имени которого работает бот; пусто — единственный активный пользователь; если активных несколько — ошибка при старте |
| `SCHEDULE_TIMEZONE` | `Europe/Dublin` | часовой пояс новых расписаний |
| `BOT_SCHEDULED_REPORT` | `changes` | `changes` — отчёт о плановом запуске только при новых `queued` или ошибках; `always` — после каждого |

Бот использует те же настройки, что и CLI: `DATABASE_URL`, `AGENT_BROWSER_SOCKET`, `OLLAMA_*`,
`JOB_TRACKER_*`.

## Кто может командовать ✅

Бот отвечает только на сообщения и кнопки из чата `TELEGRAM_CHAT_ID`. Сообщения из других чатов
пропускаются молча, без ответа об ошибке. Команды старше 10 минут (отправленные, пока бот был выключен)
тоже пропускаются, поэтому перезапуск не повторяет старый `/run`.

Все действия выполняются от имени одного владельца: его вакансии, поиски, банк ответов и расписания.
Задачи бота работают только с этим владельцем. Для сравнения, CLI без `--user` обходит всех активных.

## Команды ✅

| Команда | Что делает |
|---|---|
| `/status` | вакансии по статусам, что выполняется сейчас и на каком этапе (сбор — последняя страница поиска; оценка — сколько оценено, сколько в queued и последняя вакансия; подача — только этап), последние 5 запусков, ближайшие по расписанию |
| `/run collect` · `/run score` · `/run cycle` | запустить сейчас; бот сразу отвечает «Запускаю…», в конце присылает отчёт |
| `/run apply` | заполнить формы Easy Apply из JT To Apply, стоп перед Submit; после отчёта — сообщение на каждую готовую форму с ✅ / ❌ и на каждый вопрос агента ([подача](#подача-)) |
| `/pending` | заново прислать формы, ждущие ✅, и открытые вопросы |
| `/stop` | остановить текущую задачу (дописать текущую страницу или вакансию) |
| `/schedule` | список расписаний с кнопками ⏸/▶️ и 🗑 |
| `/schedule cycle 0 9,18 * * *` | создать или заменить расписание задачи; новое создаётся **выключенным**, ответ подсказывает «включить: /on cycle» |
| `/on cycle` · `/off cycle` | включить или выключить расписание задачи |
| `/searches` | сохранённые поиски с кнопками вкл/выкл (то же поле `enabled`, что в `PATCH /api/searches/:id`) и 🗑 удалить (история прогонов поиска удаляется, вакансии остаются) |
| `/search node.js \| Remote \| +node,backend \| -java,qa` | добавить сохранённый поиск LinkedIn, сразу включённый. Обязательны только ключевые слова; дальше части через `\|` в любом порядке: `+слова` — хотя бы одно в названии, `-слова` — отсеять, `all` — не только Easy Apply (по умолчанию только Easy Apply), часть без знака — локация. `/search` без аргументов — подсказка |
| `/queued` | 10 лучших отобранных: оценка, название, компания, ссылка |
| `/answers` | банк ответов |
| `/answer <вопрос> = <ответ>` | записать ответ (`origin: telegram`); тот же вопрос в другой формулировке заменяет прежний |
| `/help`, `/start` | список команд |

Флаги к `/run` и `/schedule` пишутся после задачи (у `/schedule` — после 5 полей cron) как `ключ=значение`:

| Флаг | Задачи | Значение |
|---|---|---|
| `limit=N` | score, cycle, apply | не больше N вакансий при оценке; для apply — запусков агента (по умолчанию `APPLY_MAX_PER_RUN`) |
| `threshold=N` | score, cycle | с какой оценки вакансия идёт в `queued` (0–100) |
| `max=M` | все | предел длительности прогона, минуты (по умолчанию 60) |
| `easy` | collect, cycle | только вакансии с LinkedIn Easy Apply, на этот прогон |
| `skip-collect` | cycle | без сбора: оценка уже найденных и отправка |

Флаг, который не подходит задаче, отвергается с объяснением. `dry-run` и `no-push` в боте нет: их
место — CLI. Расписание подачи: `/schedule apply 0 10 * * 1-5 limit=3`, затем `/on apply`; оно только
заполняет формы, отправка — всегда после ✅.

## Подача ✅

- `/run apply` (или по расписанию) идёт как задача бота: одна за раз, lock браузера берёт сервис подачи
  (`apply`); если браузер занят — «занято: …». Отчёт: строка на вакансию (ready, needs_input, skipped
  с причиной, failed), затраты за сутки и лимит.
- На каждую заполненную форму — сообщение с полями, которые заполнил агент, и кнопками
  **✅ отправить** / **❌ отказаться** (данные кнопок `a:ok:<id>` / `a:no:<id>`).
  - ✅ — отправка в фоне под тем же правилом «одна задача за раз» (занято — бот так и ответит на кнопку);
    итог отдельным сообщением: отправлено и отмечено в JT, JT не ответил (отметка уйдёт следующим
    прогоном), 409 и т. п.
  - ❌ — попытка и вакансия `skipped`, причина «отклонено вручную».
- Каждый вопрос агента — отдельным сообщением. **Ответ реплаем** на него записывается в банк ответов
  (`origin: telegram`); когда закрыт последний вопрос попытки, вакансия снова `queued`, и следующий
  `/run apply` заполнит форму заново. Реплай на другое сообщение — обычный текст («Не понял»).
- Плановый `apply` присылает отчёт, если есть готовые формы, вопросы или проблемы.

Подробно о подаче — [applications.md](applications.md).

## Задачи и отчёт ✅

Задачи выполняются в процессе бота через те же сервисы, что и CLI (`createCollector`, `createScorer`).
Общие прогоны находятся в `server/scripts/pipeline-tasks.ts` (`collectJobs`, `scoreOwners`, `runCycle`),
форматтеры итогов — в `server/scripts/pipeline-cli.ts`. Поэтому `cycle` в боте ведёт себя как
`npm run cycle`:

- если брокер браузера недоступен или браузер занят, сбор пропускается, а отбор идёт;
- если Job-Tracker не настроен, отбор пропускается, и это ошибка;
- если Ollama недоступна, отбор останавливается.

`collect` и `cycle` гоняют включённые сохранённые поиски владельца.

Отчёт содержит те же итоговые строки, что печатает CLI («Итог цикла: …»), и длительность прогона.
Если появились новые `queued`, к отчёту добавляются 5 лучших `queued` со ссылками. Построчный вывод
(каждая вакансия, каждая страница) уходит в журнал процесса, а не в Telegram.

Когда приходит отчёт:

- после `/run` — всегда;
- после планового запуска — только если есть новые `queued` или проблемы: ошибка поиска, ошибки
  оценки, недоступная модель, ошибка отправки в JT, «занято». При `BOT_SCHEDULED_REPORT=always` — всегда.

## Одна задача за раз ✅

- Внутри бота одновременно идёт только одна задача. Новый запуск, ручной или плановый, получает
  ответ «занято: cycle, запущено N мин назад». Такой запуск попадает в историю со статусом `busy`.
- Для браузера бот берёт тот же файловый lock `server/data/browser.lock`, что и CLI
  ([agent-runner.md](agent-runner.md#блокировка-браузера-pluginsbrowser-lockts)):
  - `/run collect` берёт lock на весь прогон (`task: bot:collect`); если lock держит, например,
    `npm run collect` в терминале, ответ — «занято: браузер — collect (pid …), запущено N мин назад»;
  - `cycle` берёт lock только на сбор: если браузер занят, сбор пропускается с этой причиной, отбор идёт.
- `npm run collect` в терминале, пока бот собирает, падает с «браузер занят: bot:collect …».
- Бот local-agent об этом lock не знает. Пока идёт сбор по расписанию, не давай ему задач с браузером.

## Расписание — домен `schedules` ✅

- Таблица `schedules`: `userId`, `task` (`collect` | `score` | `cycle`), `cron` (5 полей), `timezone`,
  `enabled`, `options` (JSON флагов), `lastRunAt`, `lastStatus`, `lastSummary`. На задачу одно
  расписание (`@@unique([userId, task])`). Новое создаётся выключенным, а при замене прежний `enabled`
  сохраняется.
- Таблица `task_runs`: `task`, `trigger` (`manual` | `schedule`), `scheduleId` (при удалении
  расписания становится `null`), `startedAt`, `finishedAt`, `status`, `summary` (текст отчёта, до 2000
  символов). Статусы: `running → ok | error | aborted`, а `busy` означает, что запуск не начался.
- Выражения cron разбирает библиотека `croner` (`plugins/cron.ts`, порт `CronCalendar` в
  `ScheduleTypes.ts`), с учётом часового пояса. В `Europe/Dublin` 9:00 остаётся 9:00 и после перехода
  на зимнее время: 08:00Z летом, 09:00Z зимой.
- Планировщик (`Scheduler` в `scripts/bot-runtime.ts`):
  - при старте, после каждого изменения расписаний и после каждого срабатывания считает ближайший
    запуск всех включённых расписаний и ставит один `setTimeout`;
  - таймер никогда не ждёт дольше часа, затем пересчитывает план: так замечается сдвиг часов;
  - перед запуском проверяет, что расписание не изменилось и не выключено;
  - пропущенные запуски не догоняются: если бот был выключен или машина спала дольше 5 минут после
    времени запуска, этот запуск пропускается, а в журнал пишется строка «пропущен запуск…»;
  - если два расписания совпали по времени, второе получит «занято».

HTTP API у расписаний нет: управление идёт только через бота.

## Клиент Bot API ✅

`server/plugins/telegram.ts` построен на `fetch`, без библиотеки. Методы: `getUpdates` (long polling
по 50 с), `sendMessage`, `editMessageText`, `answerCallbackQuery`.

- На 429 клиент ждёт `parameters.retry_after` и повторяет запрос, до 3 раз. Если `retry_after` больше
  5 минут, клиент сдаётся.
- На 5xx и сетевые ошибки клиент повторяет запрос с растущей паузой, на остальные 4xx сразу выдаёт ошибку.
- Токен стоит в URL каждого запроса, поэтому в ошибках (`TelegramError`) нет ни URL, ни исходной
  ошибки fetch: только метод и описание от Telegram.
- Сообщения отправляются в HTML, весь текст из данных экранируется. Сообщение длиннее 4096 символов
  делится по строкам.
